## 6. 这一轮查出的四个缺陷与处置

### 6.1 零成交（`fcb660f`）—— 已修

`research-dataset.ts` 的 `needsVolumeEvidence(spec.strategy)` 把「信号是否需要量能证据」与「**执行**是否需要逐日交易规则」混为一谈。修法：逐日事件行无条件构建；量能专属合并仍条件化。
**验证**：3 只股票上 `evidenceRows` 0 → 15922、成交 0 → 6716，「有事件但零成交」的记录数为 0。

### 6.2 三个抓取期陷阱 —— 已修

逐证券派生数据由**抓取时的 spec** 决定，而驱动器对所有预设只用一个 spec 抓一次。三个实例：分钟线、`eventCoverage`、`volumeEvidence`。
**教训（已写进注释）**：只要一种派生数据可能被任何消费方需要，就不该由抓取 spec 门控。

### 6.3 复权因子把股改对价当除权（`1aca529` 记录，修复在工作区未提交）—— 已修 + 已重跑

**这是本项目至今最实质的正确性缺陷。**

- **机制**：`adjustmentFactors` 把所有 `category === 1` 且 `bonusRatio > 0` 的事件一律按除权公式处理，**不区分「新发股份摊薄」与「股改对价转让」**。
- **物理判据**：`sh600000` 2006-05-12 的 category-5 记录显示**总股本 3,915,000,000 → 3,915,000,000 完全未变**（只有流通股 ×1.3）。若真按 10 送 3 除权，理论除权价 8.354、涨停 9.19，而当日**最高 10.66 远高于涨停，物理上不可能**。
- **影响**：71/280 只受影响，事件之前 **11.1% 的 K 线**失真，集中在 **1997–2006**（验证段 2017–2022 不受影响）。失真形态：该日**原始 −5.99% 被复权成 +22.22%**（差 28.2 个百分点）。
- **修法**：按同日股本变动记录的总股本是否增加区分。总股本增加 → 沿用除权公式；**总股本不变 → 把配股/送转项归零，但派现仍照常调整**（整条跳过会把真实派现也丢掉——这个过度修正被执行者的逐日比较当场抓出）。
- **判据集合用 category 2–10 而非单个 category 5**（转让类在 category 5 只有 71 起，另有 3 起记在 category 3；真实摊薄类若只看 category 5 会漏掉 444 起）。
- **边界（先量后定）**：总股本增加 519 起/156 只（沿用公式）；总股本不变 74 起/74 只（本次修复）；总股本减少 1 起（无依据 → 沿用公式）；**同日无股本变动记录 422 起/116 只、涉及 806,902 根 K 线 → 维持现有行为**（它们呈逐年送转节奏，当成转让会把 80 万根 K 线的真实除权抹掉）。

**验证（四项）**：目标个案跳幅 1.3 → 1.000000、复权收益 +22.2192% → −5.9853% = 原始收益；**未受影响证券 206 只/527,504 个比较点逐字节不变**；与平台因子交叉验证的比值常数 **0.7692/0.8403/0.8397 → 1.0000/1.0000/0.9992**；全量 461 文件 / 11,500 项 / 0 失败。

**影响刻画（55 个预设逐项）**：19 个完全不变（34%）、36 个变动（66%），成交变动区间 −1.2% ~ +4.1%；量价族完全不变（其有效池 59/280）。**这就是「全部作废重跑而不是按幅度挑选」的依据。**

### 6.4 尚未闭合的口径分歧（`sh600036`）

本地跳幅 1.259630（GBBG 对价比例 10 送 2.596）vs 平台 1.086268（**恰好等于实际股本倍数**）。**30 个平台跳点中 29 个与我们的跳幅吻合，但这 29 个对两种候选口径都成立、不具判别力**；唯一具判别力的观测支持「按实际股本倍数」。

**本阶段维持现有口径**，理由不是证据支持它，而是：判别性样本只有 1 起；替代规则在**配股**（分子要加 `rights × rightsPrice`）与同日派现上的配合需要独立推导，只换除数会引入新错误。

## 9. 已知陷阱

### 9.1 `vitest` 不做类型检查（本项目刚踩过）

本仓库 vitest 走 esbuild **剥类型**。所以：

- **「全量 N 项 0 失败」不能证明 `tsc` 通过**。两者是独立的门
- 宣称 `tsc` 通过前，必须在**最后一轮改动之后**真的跑一次
- 改动若发生在验证启动之后（比 `stat` 的 mtime 与验证启动时刻），**那次验证对该文件不成立**，必须重跑

本项目曾把 5 个类型错误推上 master（全在测试桩上：字面量被放宽为 string 报 TS2345；未导入 `Bar` 报 TS2304）。

### 9.2 静默产出全零

已吃过三次：`?? []` 把缺失变成空数组、`.bin` 缓存复用、半写归档被 reuse。

- 驱动器现在有 **`evidenceRows === 0` 即中止**的守卫（含自诊断）
- 续跑前**先核对每个归档可解析**
- 每批跑完自检：该批 `raw/` 下**不得有本次修复之前写入的文件**

### 9.3 结果键塌缩

161/162 个组合预设展开后 `spec.strategy` 相同。**任何按 `spec.strategy` 做结果键的地方都会把 162 个组件塌缩成一行**，并据此得出「组件无效果」的假结论。归档键与结果表行键必须是 **preset id**。

同理：`records` 有 342 条带 `presetId` 但只有 **252 个不同 presetId**（多方法共享同一预设各发一条记录）。**按方法维度汇总会重复计数。**

### 9.4 计数口径

结果表的成交数用 `sum(partitions[].simulation.statistics.count)`（**已闭合往返计数**）；另一口径 `sum(...trades.length)`（**数组长度，含未闭合/部分成交**）在部分行上不等。**两者都对，但必须声明用的是哪个。**

### 9.5 「有效池为 0」不等于「策略无效」

它通常是**数据覆盖缺口**。当前按股拒绝的主因是量价族的**量能可比性覆盖**（除权事件的 GBBQ `floatSharesBefore/After` 逐条齐全）——与策略优劣无关。

### 9.6 其他

- **`dataset.actionCoverage` 永远不会是 `"full"`**（只有 `partial`/`missing`）。本地 GBBQ 覆盖对「某段前缀无公司行动」只是**较强证据，不是证明**
- 五分钟锚窗口与日线/月线锚**分表**，不得跨表比较（bar 粒度与逐日可用性不同）
- 平台侧：`get_index_stocks` 的 `date` 生效且不回溯；`profit_report` 是快报表；**估值表覆盖不到 2003–2004**；`run_query` 对财报恒 0 行
- **`capturedAt` 是调用方填的标签**，不得当作排序依据决定「哪份快照最新」——要用文件系统事实（mtime）
- 远端 `run.ps1` 在某些错误下**退出码仍为 0**（错误被吞）

## 10. 验证与提交纪律

### 10.1 分层验证

- **L1**：`pnpm verify:spot`（快速定向）
- **L2**：`npx tsc --noEmit` + 相关族测试 + `npx tsx scripts/audit-trading-methods.ts`

**同一批内不要为每个方法重跑契约套件** —— 契约套件是注册表驱动的，扩展注册表即可。

### 10.2 结论可核查（`executor-brief.md §6.5`）

- 引用行号必须**引用该行的内容**
- 不得把执行阶段的成因归给零样本项
- **无逐项证据不得给百分比结论**
- 改了既有断言要**逐处**给出：原断言在保护什么属性、为何该属性在新设计下由别处保证或不成立
- **严格区分「已证实」与「推测」**

### 10.3 产出物

- 每次交付写 `.codex-runs/<批次>-delivery.md`，含：做了什么、改动点（`文件:行号`+引用内容）、实测数字、未解决项、验证命令与退出码
- 方法表 `docs/trading-skills-method-map.json` 是**唯一进度真源**
