## 2. 第一波：工程底座（先做，后面每一批都要靠它）

### 0A 测试并行化与防卡死

> 进度：已完成（2026-09-29）。整组并行，单测超时 60 s；连续 3 次全量 0 失败，562 s → 194–209 s。无需改分类器，也不需要按 worker 派生数据目录（setup 早已按文件隔离）。
- **现状**：433/531 个文件被归为串行。`scripts/lib/test-projects.ts` 会追踪运行时 import，碰到数据库、数据目录或未知的动态 import 就判为串行。
- **做法**：
  1. 先测基线：全量耗时、串行组耗时，以及最慢的 20 个文件。
  2. 每个 worker 使用独立的 `QUANT_DATA_DIR` 和 SQLite 文件，在 setup 中按 worker id 派生。这样"碰数据库"本身不再构成串行理由；只有真正共享外部资源的文件（koffi DLL 单进程、端口、全局文件）才留在串行组。
  3. 加卡死保护：单文件超时、`--reporter=hanging-process` 诊断，全量脚本设总超时，超时时输出当前在跑的文件。
- **验收**：全量耗时降到基线的 40% 以下；串行文件 ≤ 60 个，且每个都写明理由；连续 3 次全量结果一致、无卡死。`verify:batch` 零失败的语义不变。

### 0B 浏览器验收正规化
- 把第一轮留下的性能与交互脚本收拢成 Playwright Test 项目（约 15 个 spec），逐步覆盖约 110 个零散脚本。优先收拢的有：`chart-perf`、`chart-keys`、`chart-drawings`、`intraday`、`chart-compare`、`workbench-perf`、`persist-cache`、`screen-perf`、`backtest-perf`、`trade-review-perf`，另新增 keep-alive 巡检。
- 共用 fixture：构建一次；启动隔离服务；灌入种子数据（交割单生成脚本从临时的 `scripts/_gen-ths.ts` 转正）。
- 引入 `perf-budgets.json`，把第一轮的数字写成上限（留 30% 余量），例如：画线工具切换 ≤ 8ms、回测出结果 ≤ 1.5s、2222 笔成交的复盘 ≤ 1.5s。超出即失败，防止性能回退。
- **依赖决定**：`@playwright/test` 作为 devDependency，替代现在 `~/.agent-tools/playwright` 的借用方式（见 §6 D4）。

### 0C 静态检查
- 引入 ESLint，只开启高价值规则：`react-hooks/rules-of-hooks`（error）、`exhaustive-deps`（warn）、`no-floating-promises`（针对 server）。先按现状生成基线，只拦新增违规，不做全仓格式化。
- **验收**：`pnpm lint` 加入 `check`；把 #310 那类写法作为反例放进测试，确认会被拦下。

### 1A keep-alive 治理（实测问题，优先级最高）

> 进度：第 1 步已完成（2026-09-29）。闲置 10 s 内隐藏面板 0 请求，主线程 470–745 ms → 106–165 ms，堆约 54 MB。第 2 步（LRU）等待 D3。
1. **隐藏面板零请求**：修掉 §1 列出的 4 类违规轮询（先定位到具体组件）。0B 中加巡检 spec：逛完全部页面、停在任一页，10 秒内隐藏面板发出的 tRPC 请求必须为 0。
2. **容量上限（LRU）**：常驻面板默认保留最近 N 个（建议 6；行情图表页可固定常驻），被淘汰的面板卸载，但保留 URL/查询缓存可恢复的状态。
3. **验收**：逛完全部页面后，闲置 10 秒的 CPU ≤ 单页水平 ×1.3，DOM ≤ 1.5 万，堆 ≤ 35MB；回到最近 N 个页面仍然瞬间切换，滚动位置和图表状态保留。

### 1B 路由级代码分割

> 进度：已完成（2026-09-29）。首屏 JS 约 520 KB → 230–290 KB；首次切换 22–136 ms，无 hydration 报错。

- **验收**：首屏 JS 降至 ≤ 300KB（`/market` 除外，它自带 lightweight-charts）；首次切换到未访问页面 ≤ 250ms（含加载 chunk）；不出现 hydration 报错（第一轮的 #418 教训）。

## 4. 第三波：贯通每日工作流（功能与体验）

按 roadmap 的工作流：盘前观点 → 浏览 → RPS 候选池 → 午尾盘预选 → 收盘确认 → 样本验证。每项开工前先核实现状；以下是待验证的差距假设，不是结论。

### 2A "今日就绪度"总览
- 在总览页用一个面板回答"今天能不能开工"：财联社报告是否为当日且完整、本地日线是否到上一交易日、RPS 发布日、gbbq 更新时间、监控是否在跑、通知渠道是否正常。每项都能点击跳到对应模块修复。
- 对标：通达信"盘后数据下载"状态、TradingView 数据延迟标识。

### 2B 候选 → 图表 → 信号 → 台账 一键贯通
- 在选股结果、RPS 排行、预选、信号台账等列表里，用 ↑/↓ 或 PageUp/PageDown 逐只切换右侧图表（通达信自选股翻页）；图表上自动叠加该股的信号和成交点。
- 统一"加入自选/加入监控/记一笔"的快捷动作（右键菜单加快捷键），并与 `security-select` 键盘精灵不冲突。
- 回测成交可点击，跳到行情图表对应日期并标出买卖点。

### 2C 收盘流水线
- 一键（或定时）串行执行"日线齐备检查 → RPS 发布 → 信号确认 → 台账观测"，在任务中心显示整体进度和每步证据。任一步失败即停下，给出原因和重试入口。
- 仍遵守：15:05 只是最早检查时刻，不代表行情已更新；数据未齐不推进。
