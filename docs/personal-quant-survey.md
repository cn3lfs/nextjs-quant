# 个人量化软件功能与模块调研

调研日期：2026-09-13。目的：给"一个人使用、单机为主、A 股为主"的量化软件划定应有的功能边界与模块划分，参考主流量化系统的实际做法，并对照本仓库（观澜）现状指出差距。

本文是**外部调研与设计参考**，不是交付计划。范围裁定仍以 [roadmap.md](roadmap.md) 为准，落地顺序以 [next-plan.md](next-plan.md) 为准。文中提到的能力不代表本仓库已实现。

---

## 1. 结论先行

1. **个人量化系统不是机构系统的等比缩小版。** 机构的核心成本在多策略并行、多账户合规、低延迟撮合；个人的核心成本在**数据可信度、研究不自欺、单机可靠性**。把预算花在撮合延迟上，对个人几乎没有收益。
2. **最应该被当成一等公民的是"数据层 + 研究记录层"，而不是策略层。** 主流系统里真正难以替代的部分是证券主档、公司行动、时点（point-in-time）语义和实验台账；策略代码本身反而是最容易重写的部分。
3. **模块划分建议直接采用"数据 → 研究/因子 → 策略信号 → 组合与风控 → 执行 → 复盘"六段流水线**，这是 LEAN（Universe → Alpha → Portfolio → Risk → Execution）与 vn.py（Gateway → EventEngine → 策略引擎 → 风控 → OMS）两条主流路线的公约数。个人系统可以合并其中几段，但**不能把它们混在同一个函数里**，否则无法单独验证。
4. **回测必须默认被怀疑。** 幸存者偏差、前视偏差、多重检验三者会相乘；一个没有记录"试了多少次"的回测结果在统计上无法解释。
5. **实盘/模拟执行的最小控制集是固定的**：持仓与单笔上限、亏损上限、下单频率上限、独立于策略进程的 kill switch、与券商状态的定期对账。缺任何一项都不应接实盘。

## 2. 主流系统的模块划分对照

| 系统 | 定位 | 模块划分要点 | 对个人系统的借鉴 |
| --- | --- | --- | --- |
| **QuantConnect LEAN** | 开源 C# 引擎 + 云平台 | Algorithm Framework 五段：Universe Selection → Alpha（产出 Insight）→ Portfolio Construction（产出 PortfolioTarget）→ Risk Management（调整 target）→ Execution；引擎层另有 DataFeed / TransactionHandler / BrokerageModel / ResultHandler | 五段式职责分离是最清晰的抽象；"信号"与"目标仓位"分成两种对象，是个人系统最值得抄的一条 |
| **vn.py (VeighNa)** | 国内开源实盘框架 | EventEngine 事件驱动内核；Gateway 抽象柜台（CTP 等）；MainEngine/OmsEngine/LogEngine；应用层拆包：ctastrategy、cta_backtester、datamanager、riskmanager、algotrading（TWAP/VWAP/Sniper） | 回测引擎与实盘引擎"同一套策略 API"是硬要求；风控作为独立 app 而不是策略内部逻辑 |
| **Backtrader** | 经典 Python 回测框架 | Cerebro 调度 + Data Feed + Strategy + Indicator + Analyzer + Broker（含佣金滑点模型）+ Sizer | Analyzer/Sizer 的拆分值得学：绩效统计和仓位计算都不该写在策略里 |
| **VectorBT / 向量化派** | 参数扫描与批量研究 | 全向量化，秒级跑数万组参数 | 适合做参数面稳定性检查，但天然容易前视，需要与事件驱动回测互为交叉验证 |
| **Microsoft Qlib** | AI 量化研究平台 | 数据层（表达式因子 + Alpha158）→ 模型层（LightGBM/LSTM/Transformer）→ 实验管理（MLflow）→ 简易回测；**无实盘接口** | 因子表达式语言 + 实验版本管理是研究层的标杆；提醒了"研究平台"和"交易系统"可以是两个东西 |
| **NautilusTrader** | Rust 内核事件驱动 | 同一内核跑回测与实盘，强调纳秒级时间戳与事件顺序一致性 | "回测与实盘共用同一事件序列语义"是避免实盘漂移的根本做法 |
| **迅投 QMT / miniQMT** | 券商端本地客户端 | 本地运行策略，xtquant 原生接口下单，全推行情、Tick 与盘口回放；支持股票/两融/ETF/可转债/期权/期货；可装第三方库 | 个人 A 股接实盘的现实路径；代价是必须保持机器开机 |
| **恒生 PTrade** | 券商端云托管 | 策略托管在券商机房，回测→模拟→实盘闭环；不支持期权期货，不能访问外网 | 免维护但受限；说明"托管 vs 本地"是个人系统的第一个架构岔路 |
| **掘金量化** | 第三方多市场平台 | 统一多品种框架 + 策略社区/分成生态 | 社区与策略市场不是必备模块，但"策略元数据可分享"影响接口设计 |

两条主流路线的差别值得明确：**LEAN/Qlib 偏"研究与组合"，vn.py/Nautilus/QMT 偏"执行与实盘"。** 个人系统通常先要前者，只有在策略已被证明之后才需要后者。

## 3. 应具备的功能与模块

按数据流分层。每层给出：职责、必备功能（MVP）、进阶功能、常见坑与验收口径。

### 3.1 数据层（最重要，优先级最高）

**职责**：把外部行情、公司行动、基础资料变成可复现、可追溯、带时点语义的本地事实。

必备：
- **证券主档（securities master）**：代码、名称、上市/退市日期、所属市场、别名与曾用名、状态（正常/ST/停牌/退市）。QuantStart 的经典建模是 exchange（原始来源）/ vendor（逐字段来源）/ instrument 三层。
- **行情存储**：日线为底线，分钟线按需要。存**原始未复权**价格，复权在读取时计算。
- **公司行动表**：拆分、送转、分红、配股、并购、代码变更。与行情**分表存放**，通过因子在查询边界上做 join。
- **数据质量检查**：缺失交易日、价格尖刺（常见于未处理的拆分）、成交量为零、OHLC 逻辑违例、重复与乱序。
- **来源与口径标注**：每条序列必须能回答"来自哪里、什么时候取的、是否复权、单位是什么"。
- **交易日历**：不能用"文件有更新"冒充"今天是交易日且行情已更新"。

进阶：
- **双时间（bitemporal）语义**：同时记录 effective date（事实发生日）与 knowledge date（你知道它的日期），使回测能重建"当时已知的世界"。财务数据与指数成分股尤其需要。
- **点时数据（PIT）**：财报修订、指数成分调整、分析师预期。买不到 PIT 数据时的务实替代是**保守滞后**（例如财报一律按公告日 +N 日可用）。
- **增量更新与断点续传**、本地缓存分层（尾窗缓存 / 全量历史）。
- 存储选型：个人规模下 SQLite/Parquet 足够；Tick 级别再考虑 ClickHouse 或 ArcticDB（后者提供版本化"时间旅行"与 symbol/library 组织）。通用时序库（InfluxDB/Timescale）对盘口与公司行动的建模支持弱。

常见坑：
- 用"当前指数成分股"回测历史 → 幸存者偏差，剔除了最差的样本。
- 前复权价格回到很早的年份会变得极小，按"低价股"选股实际上是在买"未来会拆分的股票"——这是**由复权引入的前视偏差**。
- 把不同来源的快照拼成一条历史序列，形成口径不明的数据。

验收口径：任意一根 K 线能追溯到源文件与解析规则；同一请求两次返回同一 hash；公司行动缺失时明确报错而不是静默补零。

### 3.2 研究与因子层

**职责**：从数据生成可计算、可复用、可版本化的特征与筛选结果。

必备：
- **指标库**：唯一共享实现，全历史递推，窗口不足返回 null 而不是补零（回测与实盘必须调用同一份实现）。
- **选股/筛选**：规则表达式或公式语言，结果可分页、可导出、可复现（保存公式版本 + 参数 + 数据快照）。
- **横截面工具**：排名（RPS 类）、分组、行业/概念中性化、去极值与标准化。
- **可视化**：K 线 + 多副图指标 + 画线工具；这是个人系统里验证信号最高效的环节，不是可有可无的装饰。

进阶：
- **因子表达式语言**（Qlib 风格）与因子库；注意多数表达式引擎对**截面算子**支持弱，需要显式设计。
- **因子评价**：IC/RankIC、分层收益、换手率、衰减曲线、因子相关性矩阵。
- **ML 管线**：训练/验证/测试按时间切分，禁止随机打散；实验用 MLflow 之类做版本记录。
- **事件与另类数据**：公告、新闻、龙虎榜；必须带时点，且不能用"后来补采的新闻"进入当时已知信息。

常见坑：未来函数（在 t 时刻使用了 t 之后的数据）；标准化时用了全样本均值方差；指标在数据缺口后被重置导致回测与实盘不一致。

### 3.3 策略与信号层

**职责**：把特征变成明确的、带时点的交易意图。

必备：
- 策略模板与生命周期钩子（初始化 / 每根 K 线 / 成交回报 / 收盘）。
- **信号对象化**：方向、标的、时间、置信度、有效期——即 LEAN 的 Insight。信号不等于下单。
- 参数集中声明，可保存、可比较、可版本化。
- 策略状态持久化（重启后不丢失持仓认知与基线）。

进阶：多策略并行与信号合并（等权、Black-Litterman 式观点融合）、策略间冲突处理、策略开关与灰度。

常见坑：把仓位计算、风控、下单全塞进策略函数，导致任何一段都无法单独测试。

### 3.4 回测与验证层

**职责**：在尽可能诚实的假设下估计策略表现，并量化这个估计有多不可信。

必备：
- **事件驱动回测**，撮合发生在信号之后的下一个可成交时点（A 股常见做法：次日开盘）。
- **交易规则建模**：T+1、100 股一手、涨跌停无法成交、一字板与停牌、资金不足。
- **成本模型**：佣金（含最低 5 元）、印花税、过户费、滑点；成本参数必须显式可追溯。
- **绩效分析**：年化、最大回撤、Sharpe、胜率、盈亏比、换手、单笔分布、资金曲线。
- **前视隔离测试**：用自动化测试证明回测在 t 时刻拿不到 t 之后的数据。

进阶：
- **Walk-forward 滚动检验**：在样本内优化、样本外检验，窗口向前滚动覆盖全样本。常见参数为优化窗 2–4 年、样本外 3–6 个月、滚动窗优于锚定窗。
- **最终留出集**：最近 10–20% 数据在回测和滚动检验都完成前不许碰。
- **多重检验修正**：记录尝试次数；用 Deflated Sharpe Ratio（按试验次数、偏度、峰度调整显著性阈值）与 PBO（回测过拟合概率）评估。Harvey 等人对因子的建议门槛是 t > 3.0 而非 2.0。
- **稳健性**：参数面平原而非尖峰、随机起始日、成本敏感性、子区间与不同市场状态分段。
- 组合级回测：现金管理、再平衡、分红再投资。

常见坑（这些偏差会**相乘**）：
- 幸存者偏差 + 一根 K 线的前视 + 零成本假设，三者叠加足以把噪声变成"圣杯"。
- 只报告最终曲线不报告试验次数——这是几乎所有公开回测缺失的关键信息。
- 经验法则：把回测 Sharpe 打五折作为实盘预期；优先选 1–3 个参数的简单策略。

验收口径：回测结果附带数据快照 hash、规则版本、成本参数、试验次数与样本外表现；无法复现的结果不进入决策。

### 3.5 组合、仓位与风控层

**职责**：把信号变成目标持仓，并在下单前施加约束。这一层必须独立于策略。

必备：
- **仓位算法**：固定金额 / 固定比例 / 波动率倒数 / ATR 止损反推 / 凯利分数（实践中用 1/4–1/2 凯利）。
- **单标的与总持仓上限**、行业与概念集中度上限。
- **止损止盈**：结构止损与固定比例止损；明确记录"止损单可能以市价滑点成交，不是硬性亏损上界"。
- **组合级回撤限制**：LEAN 的 MaximumDrawdownPercentPortfolio 是标准做法，超限即减仓或清仓。
- **风控可组合**：多个风控模型叠加（组合回撤 + 单标的浮盈回吐）。

进阶：相关性与集中度矩阵、风格暴露、压力测试、逐笔归因（择时 vs 选股 vs 成本）。

### 3.6 执行层（模拟盘 / 实盘）

**职责**：把目标仓位变成委托，并维护"系统认知"与"券商事实"的一致。

必备：
- **OMS 最小不变量：确认丢失 = 未知状态，不等于可以重发。** 这是个人系统最容易写错、后果最严重的一条。
- 委托生命周期状态机（待报/已报/部撤/已成/废单）与幂等的客户端订单号。
- **定期对账**：与券商持仓、资金、成交对账；出现差异立即停止交易而不是自动修正。
- **Kill switch**：独立于策略进程，明确定义作用域（阻止新单 / 撤销活动单 / 停止策略 / 平仓是四件不同的事）；并且必须在真实持仓上演练过一次。
- 下单频率与重复单保护（跑飞的循环比坏信号更常见）。
- 行情新鲜度检查：数据过期时拒绝下单。

进阶：算法拆单（TWAP/VWAP/Sniper）、多账户、模拟盘与实盘同接口切换。

个人系统的现实取舍：A 股散户可行的实盘通道基本是券商提供的 QMT/miniQMT（本地、需开机）或 PTrade（托管、受限）。是否接实盘应当是**策略被证明之后的决定**，不是系统设计阶段的默认目标。

### 3.7 监控、通知与运维层

必备：
- 定时调度与任务中心（任务状态、失败原因、可取消、可重试）。
- **告警覆盖**：行情过期、数据源断连、策略循环延迟、心跳失败、持仓/委托与券商不一致、连续废单、异常下单量、风控触发。
- 推送通道（IM 机器人等）+ **可靠投递 outbox**：限流、重试上限、过期丢弃、去重编号；"平台已接受"不等于"人已读到"。
- 日志与审计：时间戳、输入、决策、委托、券商响应、配置版本全部留存。
- 单机可靠性：进程崩溃恢复、重启后重建基线、多实例互斥（避免网页版和桌面版重复发信号）、休眠/关机期间监控缺口需要如实标注。
- 凭证安全：系统级加密（Windows DPAPI 等）存储，不写进业务库，不出现在日志。

### 3.8 记录与复盘层（个人系统最容易漏、价值最高）

必备：
- **信号台账**：所有产生过的信号不可变落库，含 T+N 前向收益，用于评估"规则在真实市场上的统计表现"，与是否实际成交无关。
- **交易账本**：实际成交、移动加权成本、可卖数量（T+1）、浮盈、除权导致的成本调整轨迹。
- **两种事实分离**：信号收益 ≠ 成交绩效，不能互相覆盖。
- 交易日志/复盘笔记：每笔交易的入场理由、离场理由、事后评价。
- 实验记录：每次回测/优化的参数、数据版本、结论，形成可检索的研究历史（这也是多重检验修正所需的"试验次数"来源）。

### 3.9 界面与交互层

必备：行情与图表、选股结果、持仓与账本、任务与告警、配置中心（数据源、通道、凭证、参数）。
个人系统的界面目标不是"炫"，而是**让每个数字都能点开看到来源**。

### 3.10 可选/AI 增强层

- LLM 用于证据解读、研究报告、公告与新闻摘要：必须是**证据受限**的（只允许引用系统给定的、带时点和 hash 的证据 ID），输出经 schema 校验，**模型输出不执行、不下单**。
- 自然语言生成策略草案：只能作为草稿，需用户确认后才运行，并明确声明不支持的条件。
- 代价与边界要讲清楚：模型调用消耗额度、结果不可复现（需固定种子/温度并记录版本），不能作为策略有效性的证据。

## 4. 优先级分级建议

**P0（不做就不算量化系统）**
数据层（主档 + 原始行情 + 公司行动 + 质量检查 + 日历）、指标唯一实现、事件驱动回测 + A 股交易规则 + 成本模型、绩效分析、信号台账、图表核对。

**P1（决定系统是否可信）**
前视隔离自动化测试、walk-forward 与留出集、试验次数记录与 DSR/PBO、风控独立成层、任务与告警、交易账本与除权审计。

**P2（决定系统是否可用于实盘）**
OMS 状态机与幂等、券商对账、kill switch、频率与重复单保护、凭证加密、单实例互斥。

**P3（锦上添花）**
因子库与 ML 管线、多策略组合与归因、算法拆单、Tick 级存储、策略分享生态、LLM 研究增强。

**个人系统建议明确不做的事**
低延迟/高频撮合优化、自建行情网关、多用户与权限体系、机构级合规报表、把"云端托管 + 全天候可用"当成早期目标（单机 + 明确标注的监控缺口更诚实也更便宜）。

## 5. 对照本仓库（观澜）现状

依据 [architecture.md](architecture.md) 与根 [README.md](../README.md)，对照上面的模块清单：

**已具备（相对完整）**
- 数据层：通达信本地二进制只读解析、证券主档与 TNF 名称、GBBQ 公司行动与显式复权换算、快照 hash 与来源标注、数据健康检查、交易日历门禁。**"存原始、读时复权"与"来源口径显式"两条主流原则已经落实。**
- 指标层：唯一共享实现、全历史递推、窗口不足 null——符合 3.2 的必备口径。
- 研究层：缠论、双突破、VCP、受限通达信公式选股（31 项未来函数硬拒绝）、RPS 横截面排名、股票池与概念分类。
- 记录层：信号台账（T+5/10/20 前向收益）与交易账本（成本/T+1/除权审计）**分离为两种事实**——这一点比多数个人系统做得好。
- 监控与通知：60 秒 tick、基线与新鲜度门禁、分级静默、outbox 可靠投递与限流重试、DPAPI 凭证、共享库租约互斥。
- 执行层雏形：同花顺模拟盘，默认零请求、需显式确认、未知结果不重试、接受委托不自动写成交——符合 3.6 的关键不变量。
- LLM 层：证据 ID 校验、Zod schema、token 记录、模型输出不执行。

**明显缺口（对照第 3 节）**
1. **回测与验证层已冻结**，当前只有"双均线研究模拟"，且不复权、未建模除权分红与涨跌停排队。按第 3.4 节的标准，这意味着系统目前**没有可用于判断策略是否有效的证据链**——这与文档中"旧回测不能用作正式策略业绩"的自我判断一致。
2. **多重检验修正完全缺失。** 更正一处：walk-forward **已经实现**（`src/lib/walk-forward.ts` + `src/server/backtest/walk-forward.ts`，滚动训练窗选参 + 不重叠测试段，并已写明"训练样本可能包含前轮测试数据""人工反复修改参数仍可能对整个历史过拟合"）。真正缺的是它的统计配套：每个 fold 从 N 个候选里取训练期第一名，**这个挑选动作抬高的表现没有被任何指标修正**——没有试验次数记录、没有 PSR/DSR、没有 PBO，也没有留出集机制。
3. **组合、仓位与风控层缺失**（roadmap 中标为冻结）。目前风险控制分散在策略与人工判断里，没有独立的仓位算法、集中度上限与组合回撤限制。
4. **执行层缺 kill switch 与定期对账机制**：模拟盘目前是"按需调用"，没有独立于策略进程的紧急停止，也没有周期性券商状态对账。接任何实盘前这是硬门槛。
5. **因子评价缺失**：有 RPS 和规则筛选，但没有 IC/分层收益/衰减这类"信号有没有用"的统计评价。
6. 多品种（ETF、指数、可转债、期货）未进入本地筛选池；周/月周期策略结构明确不可用。

**建议的下一步优先级**（仅为参考，范围以 roadmap 为准）：解冻回测层并直接按 P1 标准重建（前视隔离 + 成本 + walk-forward + 试验计数）> 因子/信号评价 > 独立风控层 > 执行层安全控制。在回测层重建之前扩展策略数量，只会增加多重检验的负担。

## 6. 关键工程取舍

| 取舍点 | 选项 | 建议 |
| --- | --- | --- |
| 回测内核 | 事件驱动 vs 向量化 | 以事件驱动为准（与实盘同语义），向量化只用于参数面扫描，两者结果需交叉验证 |
| 回测与实盘 | 两套引擎 vs 同一套 API | 同一套（vn.py / Nautilus 的核心主张），否则实盘必然漂移 |
| 复权 | 存复权价 vs 存原始+读时复权 | 存原始，复权因子独立成表，查询边界上 join |
| 时点语义 | 单时间 vs 双时间 | 财务/成分/新闻类数据必须双时间；行情可单时间 |
| 存储 | SQLite/Parquet vs ClickHouse/ArcticDB | 日线分钟线用前者；只有进入 Tick 规模才换 |
| 部署 | 本地单机 vs 云托管 | 个人优先本地 + 明确标注监控缺口；托管的代价是策略受限与外网隔离 |
| 实盘通道 | 自建 vs 券商终端（QMT/PTrade） | 券商终端；自建网关对个人无收益 |
| AI | 生成策略 vs 解释证据 | 只做证据解释与报告，生成的代码不执行 |
