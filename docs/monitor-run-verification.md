# 订阅版本与迟到任务保护

2026-09-09，当前状态核验引入远端等待后的订阅并发边界。

## 已复现的问题

`tests/monitor-tick.test.ts` 新增两个用例在修改生产代码前失败：读取行情期间用相同配置重新保存订阅，旧任务会把新基线覆盖为空；核验期间同一订阅停用后重新启用，旧任务仍生成了 1 个信号。

## 改动

保存和启停订阅均生成独立 UUID `revision`，不依赖毫秒时间戳唯一性。旧记录可继续读取，下次保存/启停获得版本。

`sameMonitorRun` 比较订阅身份、创建时间、版本、启用状态、周期、来源、证券池和策略；基线单独比较。行情读取后、状态核验后、信号落库事务内和基线保存事务内分别核对，版本或基线改变时停止旧任务写入。

新信号与通知入队在同一事务内完成，同时再检查状态和行情时效。AI 解读完成后在入队事务内核对原订阅版本；原版本未变时照常入队，重新保存或重启后的订阅不会收到旧版本解读入队请求。

## 验证

- 20 项专项通过：包含原有信号去重/时效、状态失败后重试，以及本轮替换订阅、停用重启、事务前版本/基线改变、延迟解读正常和重启分支。
- API caller 测试在固定同一毫秒连续保存两次、启停两次，4 个版本不同，基线重置；时间戳无需变化。
- 最终全量 146 文件 710 测试、类型检查、runtime/生产构建、桌面准备及冒烟通过。桌面目录 `quant-desktop-JPccfe`，行情源未改变。
- 独立库 `quant-monitor-revision-http-Wh66fT` 的真实 HTTP 保存两次、停用两次：4 个版本、空基线、始终停用、信号/报告/投递共 0。见 `output/monitor-revision-http-verification.json`。
- 并发用例通过受控回调在 I/O 或事务开始前修改数据库记录；没有真实发送，也没有调用真实模型。

## 后续边界

本轮保护生成、入队和基线保存。`notifications.drain` 对已入队通知仍主要核对渠道，尚需加入发送时的订阅版本检查；不能据此声称已经撤回或阻止所有旧队列项。已经完成的外部发送无法撤销。A–H 其余要求仍继续。
