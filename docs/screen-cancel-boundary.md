# 候选批量保存的取消边界

2026-09-09，检查阶段计数链路时发现：其他进程已把任务写为取消，执行进程的 AbortSignal 仍可能尚未收到（轮询间隔250ms），仅检查信号会继续提交后续候选批次。

修复：`putChangedBatch` 增加可选事务内前置检查，在既有 immediate 事务内、任何候选写入前执行。筛选调用在其中同时检查取消信号和数据库任务仍为 running；检查与本批写入受同一事务保护。结束保存后再检查落盘状态，阻止已取消任务走入自动快评阶段。已提交批次保留，不回滚或删除其他研究快照。

回归通过 SQLite 触发器模拟“取消状态已落盘、拥有者信号尚未送达”，在120个候选的第一批写入时记录取消。修复后只保留第一批50个，第51个起不存在；任务保持cancelled、没有结果、没有研究子任务。触发器只在隔离测试数据库使用。

负向验证：临时移除事务内检查时，相同测试实际写入120个，精确触发120≠50断言；检查已恢复后再执行全量验证。这证明测试能检出原问题，不只是验证最终状态标签。

边界是以批次事务为单位停止：取消无法插入正在提交的同一SQLite写事务；已经提交的批次是合法的既有快照，不保证取消后“零快照”。这不是对所有异步任务副作用的统一证明，原A–H目标仍需继续。

最终140文件665测试、类型检查、生产构建（含runtime）、desktop:prepare及desktop:smoke通过。`output/screen-cancel-guard-benchmark.jsonl`保留各周期首次及5次重复的实际任务、阶段和结果hash；重复结果一致，五分钟中位261.85ms/P95 278.28ms。该计时范围与既有脚本一致，不含扫描/UI/HTTP/OS冷缓存重置，分钟源仍是历史数据。本轮没有调用模型、修改通达信源文件、发消息或打包EXE。
