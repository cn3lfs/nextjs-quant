# 开发工作流程复盘与优化方案

复盘日期：2026-11-17。依据历史计划、交接、近期交付与当前执行入口，响应用户对开发效率和重复验证的质疑。本次调整工作方式，不改交易规则、研究准入、数据保护或发布权限。

## 判断与证据边界

流程确有过度验证、规则冲突和交付目标漂移。主要问题是把“多做一次核对”当成默认安全动作，缺少对新增信息、证据复用和结束条件的约束。减少单次测试耗时只能缓解症状；需要先减少不产生新结论的执行。

历史记录没有完整、统一的开发与验证工时，不能证实“开发占一成、测试占九成”的精确比例。测试数量多、策略晋级为零也都不能单独证明工作浪费。下文区分有记录的事实、流程判断和待核实项，不声称所有历史重跑都不必要。

## 暴露的问题

| 问题 | 可核查事实 | 流程影响与纠正方向 |
| --- | --- | --- |
| 交付价值被能力数量稀释 | [生命周期复盘](2026-11-15-02-optimization-plan.md#1-the-road-so-far-and-what-it-teaches)已指出方法不断扩展、证据管道投入多，而组合表达和真实日常链路仍有阻断。后续扩大理论覆盖有用户授权，不能一概视为越界 | 授权的范围仍须分成可用路径。每次先交付能实际完成的用户任务，再扩充目录；方法、测试和归档数量只描述规模 |
| 当前执行规则存在冲突 | [旧计划](2026-11-15-02-optimization-plan.md#8-execution-and-verification)要求每批完整门禁；[交接](2026-11-15-01-handoff.md)记载管理者每批提交前独立复跑；[后续交接](2026-11-16-03-handoff.md)已改为开发期定向、最后集中。旧执行说明仍要求失败后全量再跑 | 提示词叠加而没有替换，执行者倾向选择最重的要求。当前规则优先，历史只提供背景；清除常备说明里的旧流程，不让接手者自行拼规则 |
| 验证频率跟任务边界走，未跟风险走 | 历史中子任务、批末、管理者验收均出现全量要求；[闭环计划](2026-11-17-43-strategy-closure-plan.md)还同时写有子任务测试与最终完整检查 | 同一变化可能被不同角色重复验证。定向检查跟变化走，完整门禁集中到集成交付点，换人或提交不重新计次 |
| 命令组合容易重复覆盖 | [完整入口](../../../scripts/lib/local-check.mjs)包含格式、依赖、runtime、类型、lint、测试及可选构建；[命令定义](../../../package.json)中测试、类型和构建又各有包构建前置，部分前置已有缓存 | 不能把命令名称当作互不相交的证据。执行前看包含关系，完整入口覆盖后不再单跑同一检查；不据此删除必要 runtime/native 步骤，也不在本次另造调度框架 |
| 数据可行性检查暴露得太晚 | [闭环交付](deliveries/2026-11-17-04-strategy-closure.md)记录真实财务全池多年场景被关键字段 UNKNOWN 阻断，随后使用真实小样本验证阻断、合成输入验证成功链 | 关键字段资格应在放大计算前以小样本核实。最小样本能否支持核心结论，比先跑完整矩阵更有价值；合成成功必须与真实可用性分开 |
| 大量工程通过未覆盖关键用户任务 | [按钮验收](deliveries/2026-11-17-03-button-audit.md)仍发现并修复图表跳转、切换证券、任务入口及公式内存等实际问题 | 不能从测试总数推断体验已验收。用户任务应在开发中尽早贯通；UI检查选关键路径，算法边界放在低层，避免两头都重、接线仍漏 |
| 独立核对容易扩成第二套实现 | 历史任务反复要求逐笔、字节及完整材料对照；闭环交付还记录窗口外数据追加导致材料身份变化、固定窗口结果仍一致 | 独立检查对关键公式和财务事实有价值，但应回答具体风险。分别报告执行事实、结果语义和来源身份；不能把一种失败当所有结论失败，也不能用经济一致掩盖材料失败。是否需要改变身份粒度属于后续技术判断 |
| 产品错误与验证器错误混在同一收口循环 | [B2交付](deliveries/2026-11-17-02-b2-development.md)记录包级日期 fixture 错误；闭环交付记录 ORB 检查假设错误。二者均不等于整条业务链错误 | 先分类，修正真正出错的一层。失败后重跑全链并不自动增加可信度；补验范围跟影响走，原始失败与补验状态都如实保留 |
| 验收范围会随审查继续增长 | 闭环交付先有完整门禁，后续又修严格 UNKNOWN、补真实 smoke、合成成功链与 UI。部分追加发现了真实缺陷，不能全部归为浪费 | 开工明确停止条件和阻断等级。新增真实高风险应修；偏好、非阻断改善和新功能进入后续任务，不能每次审查都重开整批验收 |
| 工程交付、研究结论和自然观察容易互相等待 | [生命周期交接](2026-11-16-03-handoff.md)同时包含已完成部署、数据/容量阻断和待真实日期观察；[闭环交付](deliveries/2026-11-17-04-strategy-closure.md)也明确工程完成而真实财务数据阻断 | 分别结束与报告。工程测试不能证明收益，亏损不能反证程序有错；依赖真实时间的证据只能等实际发生。保留研究准入，但不要让它变成所有开发工作的无限返工条件 |
| 当前状态在多份文档中重复维护 | roadmap、next-plan、交付和交接重复长段计数、哈希、失败及清理过程；旧计划与常备说明继续携带不同命令、角色和数据窗口 | 多份“当前状态”容易冲突，接手后只能重新确认。范围与下一步留一个入口，细节留任务交付，长期裁定留决策；其他文档链接，不复制过程 |
| 协作中的复核责任边界不清 | 历史交接明确管理者独立复跑；近期任务又采用执行、交叉审查和主代理验收，且当前工作区有多条未提交任务的改动 | 协作不应变成每人一套完整证明。明确文件归属与集成责任，复核差异和证据适用范围；共享构建或输入发生相关变化才补验。不能从脏文件数量直接判断他人工作有误 |
| 临时产物与清理负担反过来驱动流程 | [历史优化](../2026-09/2026-09-29-01-optimization-plan.md)记录全量测试耗时与卡住；近期交付反复涉及隔离库、缓存、截图、导出、清理脚本及审批交接 | 隔离和清理不可省，但可少制造。优先小输入和已有任务目录，避免为每次复核另建整套产物；保留复现必要证据与简短失败摘要，不无限累积一次性副本 |

这些问题有共同成因：职责以“执行了哪些步骤”分配，缺少以“还缺哪条决定交付的证据”组织工作。旧的效率规则其实已经出现过，例如共享契约集中测试和不逐轮全量；问题还在于后续计划没有持续遵守，并不断叠加新要求。

## 优化后的执行流程

### 先限定本轮用户价值

接手先查当前范围、已有实现和交付证据，用简短文字说明：本轮用户能做什么，最危险的失败是什么，什么证据足以结束。复杂任务放现有计划，简单任务直接写在任务说明；不要求所有任务新建规格、报告或计时体系。

规模较大的需求拆成可使用的纵向路径，贯通输入、计算、结果和关键操作，再扩展算法或变体。用户已授权的广度继续保留，但不能用大目录掩盖主路径尚不可用。

### 先确认关键依赖，再放大投入

使用最小代表性真实输入核实数据来源、可见时点、单位及资格；新增高风险规则还需代表性成功、失败和边界。若关键输入不足，明确哪些结论不能做，停止该依赖下无意义的全池计算，继续独立开发。不得伪造数据或以合成输入冒充真实资格。

公共能力复用已有结构；只有当前功能需要或真实重复、瓶颈已出现才改造。一次重构解决本轮明确问题，不把“统一”扩成全仓基础设施项目。

### 开发中获得最短反馈

选择最能发现错误的一层验证。核心规则检查独立预期值；任务、存储与恢复检查接线和副作用；界面检查用户关键操作。共享契约由共享模块承担，各策略不复制。新增用例必须能说明会拦住什么错误，测试数量和覆盖率不充当独立交付目标。

定向检查伴随相关修改；UI主路径及数据可行性尽早暴露。阶段结束、提交或更换执行者都不自动触发全量。

### 在集成交付点集中验收

集成负责人核对差异和证据适用范围，执行尚缺的必要门禁与关键用户路径。当前完整命令及前置由工程规范和实际脚本决定，不在通用提示词里复制命令矩阵。检查已包含的步骤不重复执行；构建与已通过结果在相关代码、输入、依赖及环境不变时复用。

审查先回答是否存在会阻断本轮行为的具体问题。有真实高风险就修复并补验受影响部分；无具体阻断就结束。环境、fixture 和验证器问题分别处理，不自动清空已有有效证据，也不反复从头启动流水线。

### 交付并结束当前任务

以用户可用行为报告结果，附必要验证、限制和剩余触发条件。分开陈述工程完成、研究是否有足够证据、自然观察是否发生、外部动作是否获授权。检查失败不能写成功，零信号、亏损和未知不能互相替代。

复用一份任务交付记录与证据索引；当前计划只留摘要和下一步，历史作为历史保留。临时资源按现有授权流程精确清理，不另建多套档案或让清理交接再次扩成验证项目。

## 何时增加验证，何时停止

新增验证前应能回答：要发现哪一种具体错误？已有证据为何不能回答？什么结果会改变本轮决定？不能回答时，先明确问题，不追加运行。

| 情况 | 处理 |
| --- | --- |
| 相关执行逻辑、依赖、输入口径或运行环境变化，原证据失效 | 补验受影响的规则与链路；跨模块影响无法界定时才扩大范围 |
| 发现资金、时序、数据完整性或重复执行风险 | 阻断依赖该风险的操作，先定位修复，再验证关键反例 |
| 只改变解释文案、无关材料或任务负责人 | 检查实际影响，复用仍有效的业务证据；文案本身有口径误导时定向核对 |
| 重试没有新线索或同一输入持续确定性阻断 | 停止重试，记录原因及恢复条件，继续独立工作 |
| 缺真实日期、外部权限或必要源数据 | 标注待观察或阻断，不用更多合成回放填补 |
| 功能可用、关键风险覆盖且约定门禁已有有效证据 | 结束交付；非阻断改善另列后续，不再追加开放式审查 |

不设固定测试时间比例、审查次数或连续全绿次数。这些数字会让代理优化形式；实际约束应是每次执行带来哪条新结论。

## 本次落地与后续顺序

1. 本次先修提示词冲突：根 AGENTS 统一风险、复用和停止规则；执行者说明移除退役入口、固定角色和逐批重跑指令；工程规范同步测试范围；当前计划增加优先级入口。
2. 后续任务直接采用上述流程，不回头重跑所有历史验证、不批量删除历史测试、不新增调度器、仪表板或验证框架来证明本次规则正确。
3. 真正出现重复瓶颈时再做窄范围工具改进。例如已有检查结果能否便于接续、已有构建身份能否准确复用，均须先指出当前阻断和必要收益；这次不直接修改执行代码或来源身份契约。
4. 从后续实际交付中评估：有无重复全量及原因、是否在放大前发现数据阻断、是否按约定结束、是否又由用户发现关键链路不可用。优先利用已有日志，不为衡量效率建立另一套工作负担。

本方案已落地到文档与提示词。它能减少重复执行的制度诱因；实际节省多少时间、是否减少返工，尚需后续真实任务观察，当前不承诺未经测量的比例。
