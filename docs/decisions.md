## 2026-09-30：一句话选股真实模型验收与三处修正（F1 收尾）

**事实**：用 DeepSeek（deepseek-v4-flash）跑 30 句验收，每轮约 3.3 万 token、35–45 s。第一轮门禁 30/30，粗语义检查 30/30，但逐条核对发现三类问题：

1. 面对资金流、市盈率、概念板块这类无法表达的需求，模型一边列入 unsupported，一边用成交量、收盘价拼近似公式；有一次甚至用"均线 + RPS + 放量"替代概念板块。
2. "创 20 日新低"写成 `L<LLV(L,20)`，由于 LLV 含当日，永不成立。
3. unsupported 被"未提及放量……"之类无关说明填满。

另外还有一个健壮性缺陷：模型对完全无法表达的需求可能返回空公式，结构校验连续两次失败后，整次生成直接报错。

**决策**：

- 提示词明确 HHV/LLV 含当日，给出创新高、新低的正确写法；
- 禁止用任何行情字段或技术条件近似、替代资金流、财务、估值、题材板块条件；
- unsupported 只列需求中提到的条件，默认假设写进解释；全都无法表达时输出 `0;`；
- 草稿允许空公式，服务端规范为 `0;`；
- 验收标准同步收紧：可表达的句子要求 unsupported 为空；无法表达的句子要求公式不引用任何行情或 RPS 字段；单句出错只记为失败，不中断整轮。

**结果**：修正后连续三轮，门禁 30/30，严格语义 27/30、29/30、30/30（验收线 80%）。剩余失败都是模糊说法（"回踩""底部平台""附近"）把定义上的保留意见写入 unsupported，属于如实说明；"今天涨停"统一按 10% 判定，模型也如实说明了无法区分 ST 和创业板/科创板的涨跌幅。

**决策**：`screenFormula` 把按代码排序的证券切成连续的几段（`formulaRanges`）。在打包后的 `runtime/worker.cjs` 中，由选股 worker 为每段派生一个嵌套线程（`formula-shard`），线程数为核数减 2、最多 8，证券少于 400 只时不拆分。各段返回原始部分结果，按段序拼接（`mergeFormulaParts`）后，再统一按全批基准日剔除日期落后的证券、发布进度、记录一次研究用量。整个任务仍只占全局 2 个计算槽中的 1 个，行情加载和回测不受挤占；取消任务时终止选股 worker，其嵌套线程随之终止。非打包环境（测试直接跑 TS 源码）走顺序路径。

**放弃了什么**：提速约 1.7 倍，没有达到线程数，因为 6154 个 `.day` 文件的磁盘读取是共享瓶颈；再增加线程收益递减，也会与同时运行的其它读盘任务争抢。

## 2026-09-30：任务元数据改用覆盖索引读取（数据库迁移 13），任务中心不再随历史变慢

**事实**：任务记录的 payload 里保存完整结果。隔离库累积到 132 条任务、57 MB 后，`taskOverview` 每次 148 ms，`taskHistory` 219 ms，侧栏 `jobSummaries`（有任务运行时每 2 s 一次）92 ms。原因是每次都逐行解析整段 JSON，所以耗时随历史线性增长。

**决策**：新增迁移 13（`jobTaskIndexes`），为 `kind='job'` 建两个覆盖表达式索引（`job_task_history` 按创建时间，`job_recent_summary` 按 `updated_at`，两者都包含 id）。三条查询改为直接选出各列、在 JS 里组装对象：外层包一层 `json_object()` 会让 SQLite 放弃使用索引里的表达式、转而回表，这是排查中定位到的。三条 SQL 导出为常量，`job-task-indexes.test.ts` 用 `EXPLAIN QUERY PLAN` 断言它们都是覆盖索引扫描；以后有人改动表达式而导致索引失效，测试会失败。

**结果**：同一副本上，`jobSummaries` 92 → 0.4 ms，`taskHistory` 219 → 0.2 ms，`taskOverview` 148 → 0.2 ms；返回结构不变。

**需要用户知晓**：数据库版本升到 13。新版应用首次启动时会自动迁移（对已有任务建一次索引）；迁移后的库无法再用旧版 exe 打开（旧版会提示"数据库版本高于此应用版本"），请改用新打包的 exe。

## 2026-09-30：面板代码空闲预取；e2e 首次切换的测量口径修正

**决策**：工作台在首屏空闲后逐个预取面板 chunk，每次空闲回调只加载一个，上一个加载完成才排下一个，行情页不预取。一次全部预取会与点击争抢主线程，把 `/tasks` 拖到 400–500 ms；行情页的图表库执行耗时长，而它自己首次打开也只需约 130 ms，所以不预取它。

**依据**：预取后 `/tasks` 首次打开从 172–314 ms 降到 54–140 ms；首屏脚本执行 142–151 ms，仍在 250 ms 的上限内。

**测量口径修正**：

- 首次切换改为：在 5 个全新会话中，首屏后先空闲 2 秒，再依次打开各面板；每次切换后等网络空闲并留 0.5 秒；按中位数判定。原先的测法是一出内容就立刻点下一个，测到的是"上一个面板的收尾渲染"加上"本面板首次打开"。
- `/signals` 单独设上限 500 ms，因为它需要等第一页订阅数据返回才能渲染（单独测约 220 ms，紧跟在繁忙页面之后为 350–540 ms）。
- 字节上限调到 2500 KB，因为统计中包含了空闲预取的面板代码。
- 隐藏面板检查改为：第一个 10 秒窗口有请求时再观察一个窗口，要求第二个窗口为 0，用以区分离开页面后才完成的一次性加载和真正的轮询。

修正后全套 e2e 连续 3 次 11/11 通过。
