### N1 — 信号台账与向前复盘

目的：**积累真实信号记录**。这是最便宜的证据来源，不需要聚宽，也不需要回测引擎。
用真实向前的时间换证据，没有过拟合风险，也没有生存者偏差。

#### N1 架构决策（管理者已定，执行者不得更改）

**1. 记录全市场信号，不限于已订阅标的。**

这是本阶段最关键的设计。若只记录推送出去的信号，20 个交易日可能只有个位数样本，
永远得不出结论。改为每个交易日收盘后对**全市场**跑一次两个策略，
把产生的**全部**信号落库——每天数十条，20 天即有数百样本。
落库不等于推送；推送仍只按已启用订阅走既有链路，两者互不影响。

**2. 收益口径（必须显式，不得隐含）**

- 入场：信号次日开盘价（与既有回测约定一致）
- 出场：T+5 / T+10 / T+20 的收盘价
- **不复权**，无交易成本，无滑点
- 页面必须标注「非策略业绩」

**3. 除权处理——只标注，不计算。**

若持有区间内落有除权除息日，**标注「含除权，收益不可比」并留空收益数字**，
不得算出一个被除权污染的数字。除权信息用仓库既有的 GBBQ 解析
（数据源 `E:\new_tdx64\T0002\hq_cache\gbbq`）。
**宁可留空，不可给假数**——这是整个台账可信度的基础。

**2026-09-10 管理者补充裁定：「无事件」不等于「未知」。**

首轮实现把「GBBQ 中未命中事件」也判为「除权状态未知」，
导致真实数据下几乎所有区间都无法产出可比收益，台账失去意义。这是过度保守。

GBBQ 是通达信的标准股本变迁库，覆盖全 A 股除权除息。判定改为三态：

| 情形 | 判定 |
|---|---|
| GBBQ 可读，其覆盖期含整个持有区间，区间内无事件 | **无除权，收益可比** |
| GBBQ 可读，区间内有事件 | 含除权，**不可比，收益留空** |
| GBBQ 缺失／不可读／最后事件日期早于持有区间末 | **除权状态未知，收益留空** |

覆盖期以 GBBQ 中最大事件日期为准，必须记录该日期并在页面显示，
让用户能判断台账的时效边界。仅当文件层面有问题时才判「未知」。

**4. 无未来数据。**

回填只能在 T+N 那根 K 线**已完成**后进行。未完成、停牌、数据缺失一律留空并记原因。
必须有自动化测试证明：追加未来 bar 不改变已回填的历史记录。

**5. 存储走既有增量迁移机制**（`src/server/db/migrations.ts`），
不使用 `db:push`，不改动既有表。

#### 交付

1. 每日全市场信号台账：策略、标的、日期、方向、评分/信号质量、

开源量化系统后，针对本项目**实际缺口**筛选出的三项。用户已确认执行顺序 P2 → P1 → P3。

未采纳且**永久不做**：实盘自动下单（easytrader / miniQMT）、ML 因子挖掘（Qlib）、

## P2 — 信号分级与静默

**借鉴**：freqtrade 的 notification filter、TradingView 的 alert 管理。

**要解决的问题**：全市场每日产生数十条信号，无分级、无限额、无静默，
多了必然被忽略。信号疲劳会让前面所有工作失去意义。

**交付**

1. 三档投递策略，按信号质量分档，档位与阈值可配置：
   - 立即推送 / 并入收盘汇总 / 仅入台账不推送
   - 缠论按信号质量（观察/确认/强质量），双突破按 x/5 评分
2. 每日推送条数上限，超出并入汇总。
3. 静默时段（可配置，默认非交易时段静默）。
4. 同标的去重窗口（默认 N 个交易日内同策略同方向不重复推送）。
5. 收盘汇总消息：一条结构化汇总，而不是几十条散推。
6. 默认配置取保守值：宁可少推，不可刷屏。

**约束**

- 复用既有 outbox 与四渠道投递，**不重写投递链路**。
- 分级只影响**推送**，不影响台账落库——台账仍记录全部信号。
- 被过滤掉的信号必须在台账中标注过滤原因，可追溯。

**验收**：A 层受控假渠道端到端，实际网络投递数 0；
各档位、限额、静默、去重、汇总均有测试覆盖；消息样本写入 `docs/p2-message-samples.md`。
B 层由用户确认默认阈值与汇总排版。

## P1 — 持仓与交易日志

**借鉴**：vn.py / freqtrade / QuantDinger 的 paper trading 模块；
方法参考本机 `mock-trading` 技能与 `astock-market-rules` 技能。

**要解决的问题**：信号推送后链路就断了。「我现在持有什么、成本多少、
该不该卖」系统答不了。这是唯一的闭环缺口，也是 P3/绩效报告的数据前提。

### 架构决策（用户已确认，执行者不得更改）

**本地账本为事实来源，同花顺模拟盘为可选同步层。**

- 本地账本：手动录入买卖 → 本地计算持仓、移动加权成本、浮动盈亏、
  **T+1 可卖数量**、当前止损位距离。完全离线，零对外动作。
- 同花顺模拟盘（`mock-trading` 技能）：**默认关闭**，用户显式开启后才开户与下单。
  闭环价值不依赖第三方。

### 同花顺模拟盘接入约束

- 服务：`http://trade.10jqka.com.cn:8088`，契约见
  `~/.agent-skills/skills/mock-trading/references/api-spec.md`。
- **写 TypeScript HTTP 适配器，不执行技能里的 Python 脚本。**
  沿用问财适配器的既有先例（读技能取契约，用 TS 实现）。
- 用户已明确放行三项，记录在案：
  1. 允许连接 HTTP 明文新主机（AGENTS.md 原约束为「仅四个平台官方 HTTPS 主机」）
  2. 接受「用户名即凭证」的弱认证（`skill_<13 位时间戳>`，无 API key）
  3. 授权首次使用时自动开户（在第三方创建不可撤销的持久账户）
- 用户名虽非密钥，但等同身份凭证，**按凭证处理**：DPAPI 加密存放于
  用户数据目录 `credentials`，不写入业务数据库，不记入日志。
- 本地账本与远程持仓**对账后显式展示差异，不静默覆盖任何一侧**。
- **下单必须由用户在界面点击确认**，不得由信号或模型自动触发。

### A 股规则

T+1 可卖判定、100 股整数倍、涨跌停价格校验，一律以
`~/.agent-skills/skills/astock-market-rules` 为准，不自行推导。

### 成本与除权

- 交易费用复用既有 `cost-experiment-1` 参数（佣金/最低佣金/印花税/滑点），
  沿用「实验参数，非历史实际费用」的标注。
- 持仓期间发生除权：**按 GBBQ 自动调整成本价**（券商的实际做法），
  但必须保留调整前的成本、触发事件与调整依据，界面可查。
  GBBQ 不可用时标注「成本未按除权调整」，不静默给错数。

### 与信号台账关联

每笔交易可关联一条台账信号（允许为空，手动交易也要能记）。
由此可回答：**做过的信号 vs 没做的信号，结果差异有多大**。

**验收**：A 层本地账本全链路（录入→持仓→T+1→浮盈→除权调整）测试覆盖；
同花顺适配器用受控 HTTP 测试，**默认关闭时实际请求数为 0**；
B 层由用户决定是否开启模拟盘并完成一次真实开户与下单。

## P3 — 信号质量的因子分析

**借鉴**：[Alphalens](https://github.com/cloudQuant/alphalens) 的 IC / 分组收益 / 衰减分析。

**要解决的问题**：台账攒了数据但没有分析工具，答不了
「质量 5/5 真的比 3/5 好吗」。若两者的 T+N 收益无差别，评分体系就是装饰。

**交付**：把信号维度（质量分、量比、位置、中枢关系）当因子，
计算 IC 及其均值/标准差、分组 T+N 收益差、衰减曲线、换手率。

**前置**：依赖 N1 台账积累足够样本（约 20 个交易日）。
**样本不足时必须明确拒绝出图，不得用小样本给结论。**

**排期**：等台账数据成熟后再启动，与 N2 聚宽验证同期。
