### N1 — 信号台账与向前复盘

目的：**积累真实信号记录**。这是最便宜的证据来源，不需要聚宽，也不需要回测引擎。
用真实向前的时间换证据，没有过拟合风险，也没有生存者偏差。

#### N1 架构决策（管理者已定，执行者不得更改）

**1. 记录全市场信号，不限于已订阅标的。**

这是本阶段最关键的设计。若只记录推送出去的信号，20 个交易日可能只有个位数样本，
永远得不出结论。改为每个交易日收盘后对**全市场**跑一次两个策略，
把产生的**全部**信号落库——每天数十条，20 天即有数百样本。
落库不等于推送；推送仍只按已启用订阅走既有链路，两者互不影响。

**2. 收益口径（必须显式，不得隐含）**

- 入场：信号次日开盘价（与既有回测约定一致）
- 出场：T+5 / T+10 / T+20 的收盘价
- **不复权**，无交易成本，无滑点
- 页面必须标注「非策略业绩」

**3. 除权处理——只标注，不计算。**

若持有区间内落有除权除息日，**标注「含除权，收益不可比」并留空收益数字**，
不得算出一个被除权污染的数字。除权信息用仓库既有的 GBBQ 解析
（数据源 `E:\new_tdx64\T0002\hq_cache\gbbq`）。
**宁可留空，不可给假数**——这是整个台账可信度的基础。

**2026-09-10 管理者补充裁定：「无事件」不等于「未知」。**

首轮实现把「GBBQ 中未命中事件」也判为「除权状态未知」，
导致真实数据下几乎所有区间都无法产出可比收益，台账失去意义。这是过度保守。

GBBQ 是通达信的标准股本变迁库，覆盖全 A 股除权除息。判定改为三态：

| 情形 | 判定 |
|---|---|
| GBBQ 可读，其覆盖期含整个持有区间，区间内无事件 | **无除权，收益可比** |
| GBBQ 可读，区间内有事件 | 含除权，**不可比，收益留空** |
| GBBQ 缺失／不可读／最后事件日期早于持有区间末 | **除权状态未知，收益留空** |

覆盖期以 GBBQ 中最大事件日期为准，必须记录该日期并在页面显示，
让用户能判断台账的时效边界。仅当文件层面有问题时才判「未知」。

**4. 无未来数据。**

回填只能在 T+N 那根 K 线**已完成**后进行。未完成、停牌、数据缺失一律留空并记原因。
必须有自动化测试证明：追加未来 bar 不改变已回填的历史记录。

**5. 存储走既有增量迁移机制**（`src/server/db/migrations.ts`），
不使用 `db:push`，不改动既有表。

## P2 — 信号分级与静默

**借鉴**：freqtrade 的 notification filter、TradingView 的 alert 管理。

**要解决的问题**：全市场每日产生数十条信号，无分级、无限额、无静默，
多了必然被忽略。信号疲劳会让前面所有工作失去意义。

**交付**

1. 三档投递策略，按信号质量分档，档位与阈值可配置：
   - 立即推送 / 并入收盘汇总 / 仅入台账不推送
   - 缠论按信号质量（观察/确认/强质量），双突破按 x/5 评分
2. 每日推送条数上限，超出并入汇总。
3. 静默时段（可配置，默认非交易时段静默）。
4. 同标的去重窗口（默认 N 个交易日内同策略同方向不重复推送）。
5. 收盘汇总消息：一条结构化汇总，而不是几十条散推。
6. 默认配置取保守值：宁可少推，不可刷屏。

**约束**

- 复用既有 outbox 与四渠道投递，**不重写投递链路**。
- 分级只影响**推送**，不影响台账落库——台账仍记录全部信号。
- 被过滤掉的信号必须在台账中标注过滤原因，可追溯。

**验收**：A 层受控假渠道端到端，实际网络投递数 0；
各档位、限额、静默、去重、汇总均有测试覆盖；消息样本写入 `docs/p2-message-samples.md`。
B 层由用户确认默认阈值与汇总排版。

## P1 — 持仓与交易日志

**借鉴**：vn.py / freqtrade / QuantDinger 的 paper trading 模块；
方法参考本机 `mock-trading` 技能与 `astock-market-rules` 技能。

**要解决的问题**：信号推送后链路就断了。「我现在持有什么、成本多少、
该不该卖」系统答不了。这是唯一的闭环缺口，也是 P3/绩效报告的数据前提。

- 同花顺模拟盘（`mock-trading` 技能）：**默认关闭**，用户显式开启后才开户与下单。

  1. 允许连接 HTTP 明文新主机（AGENTS.md 原约束为「仅四个平台官方 HTTPS 主机」）

## P3 — 信号质量的因子分析

**借鉴**：[Alphalens](https://github.com/cloudQuant/alphalens) 的 IC / 分组收益 / 衰减分析。

**要解决的问题**：台账攒了数据但没有分析工具，答不了
「质量 5/5 真的比 3/5 好吗」。若两者的 T+N 收益无差别，评分体系就是装饰。

**交付**：把信号维度（质量分、量比、位置、中枢关系）当因子，
计算 IC 及其均值/标准差、分组 T+N 收益差、衰减曲线、换手率。

**前置**：依赖 N1 台账积累足够样本（约 20 个交易日）。
**样本不足时必须明确拒绝出图，不得用小样本给结论。**

**排期**：等台账数据成熟后再启动，与 N2 聚宽验证同期。

### P2 补充裁定（管理者，2026-09-10）

**问题**：执行者交付后发现，`quietOutsideTrading` 默认 true，交易窗口为
9:30–11:30 与 13:00–15:00；而日线信号最早 15:05 产生，**必然落在静默期**。
结果是「立即推送」档在当前唯一启用的周期（日线）下**结构性不可达**，
所有信号都退化为收盘汇总。

这与「质量评分若无区分度就是装饰」是同一类问题：一个永远不会触发的档位，
不如没有——它会让人误以为配置生效了。

**裁定**：**「立即推送」档绕过 `quietOutsideTrading`，但仍受
自定义静默（`quietEnabled`）、每日限额、去重窗口三者约束。**

理由：`quietOutsideTrading` 的本意是「不要在休市时打扰我」，
而收盘后 15:05 产生的强质量信号恰恰是用户最需要立刻知道的——
次日开盘前有充足时间决策。自定义静默是用户的显式意愿，仍然最高优先。

不采用「把交易窗口延长到 15:30」的做法：那会谎报交易时段，污染其他依赖该判定的逻辑。

**附带说明**（写入界面提示）：日线下「立即档」与「汇总档」实际相差约 10 分钟，
分级的价值要到 5 分钟线信号启用后才充分体现。当前仍保留分级，
因为它同时控制「仅入台账不推送」这一档，那一档是立刻有效的。

# Q 阶段：图表体验与通达信公式选股

## Q2 — 通达信公式引擎

**要解决的问题**：条件选股目前只有硬编码模板与在线自然语言两条路，
用户已有的通达信公式无法直接使用。

**方法依据**：`~/.agent-skills/skills/tdx-doc`（721 函数 / 21 分类）。
**721 个函数不可能全实现，范围必须严格限定。**

### Q2a — 语言核心与未来函数门禁

1. 词法与语法：表达式、`:=`（中间变量，不输出）、`:`（输出）、
   `;` 分隔、`{...}` 注释、参数（N1/N2…）、中文变量名。
2. 操作符与优先级：`+ - * / > < >= <= = <> AND OR NOT`，见 `functions/操作符.md`。
3. **序列语义求值**：整列计算，不是逐根标量。数据不足处返回 `null`，
   沿用 M1 的预热规则，不得用 0 填充。
4. 首批函数（约 25 个，够跑通真实选股公式）：
   - 序列行情：`CLOSE/C`、`OPEN/O`、`HIGH/H`、`LOW/L`、`VOL/V`、`AMOUNT`
   - 引用：`REF`、`MA`、`EMA`、`SMA`、`HHV`、`LLV`、`SUM`、`COUNT`、
     `CROSS`、`BARSLAST`、`FILTER`、`LAST`、`EXIST`
   - 逻辑：`IF`、`AND`、`OR`、`NOT`
   - 数学：`ABS`、`MAX`、`MIN`
   - 统计：`STD`
   `MA/EMA/SMA/STD` 必须复用 `src/lib/indicators.ts`，不另写一套。
5. **未来函数门禁（本阶段最重要的一条）**：
   维护未来函数黑名单（`ZIG`、`PEAK`、`PEAKBARS`、`TROUGH`、`TROUGHBARS`、
   `FINDHIGH`/`FINDLOW` 的未来参数形式、`REF` 的负数参数等）。
   解析后**静态检测**，命中则**拒绝执行**并指名是哪个函数、在第几行。
   **不允许「警告后继续」。** 用未来函数选出来的股票是假的，
   这与「宁可留空不可给假数」是同一条原则。

**验收**：用 `tdx-doc references/examples/条件选股公式.md` 里的真实公式做用例；
「老鸭头」那条（`EMA`/`COUNT`/`REF`/`LLV`/`CROSS`/`FILTER`/`MA`）必须能完整解析并求值，
其中 `FINANCE`/`DYNAINFO` 部分明确报「函数不支持」而非静默跳过。
未来函数用例必须被拒绝执行。

### Q2b — 函数库扩展与选股接入

扩到约 60 个函数（补 `WMA`、`DMA`、`TMA`、`HHVBARS`、`LLVBARS`、`BARSCOUNT`、
`AVEDEV`、`SLOPE`、`STDP`、`VAR`、`INTPART`、`ROUND`、`POW`、`SQRT`、`LOG`、
`MOD`、`SGN`、`BETWEEN`、`VALUEWHEN`、`RANGE`、`IFF` 等），
接入全市场选股：编辑公式 → 语法检查 → 未来函数门禁 → 全市场执行 → 结果入现有候选表。

公式可保存、可命名、可带参数。执行走既有 worker，不阻塞 UI。

### Q0/Q1 补充裁定（管理者，2026-09-10）

**1. `indicators.ts` 被修改——是管理者指令自相矛盾，不是执行者违规。**

Q1 交付第 3 项要求「指标参数全部可调」，而派工纪律里抄了「不动 indicators.ts」。
执行者按 roadmap 执行，将硬编码的 12/26/9 与 9/3/3 参数化。

**2. 模拟盘适配器必须保留原始响应。**

Q0 开户成功但股东账号查询未通过契约校验，而**适配器没有保留原始响应体**，

对第三方集成而言，拿不到原始响应就没有诊断能力。要求：

- 仍然**不得**为了拿到响应而反复重试；一次请求，保留结果。

**3. Q0 重试的边界**

补上原始响应保留后重试一次开户流程。若股东账号仍为空：
考虑「新账户需要时间开通」的可能，**最多等待一次并重查一次**，
仍失败则如实记录为「远程账户状态不可核对」，不再重试、不放宽契约。

### Q2a 补充裁定（管理者，2026-09-10）

**同花顺模拟盘的线上契约已与技能文档不符，允许按实测契约适配。**

**技能文档已落后于线上服务。**

但必须同时满足：

1. 适配层显式记录「文档契约」与「实测契约」两套字段名及其差异，
   界面可查，不得静默改成实测值假装文档就是这样。
2. 市场枚举 `9/8/:` **含义未知**，不得猜测映射到深圳/上海。

   反推不出就标注「市场代码含义未确认」，并且**不因此阻塞其余流程**。

### Q2b 补充裁定（管理者，2026-09-10）

**1. 全市场耗时标准。** 执行者实测公式选股全市场 6,145 只耗时 110.44 秒，
既有筛选 5.94 秒，并正确指出两者「并非同量级」。

管理者原话「与既有选股任务同量级」措辞不严。裁定沿用 N1 的同一原则：
**公式选股是用户主动发起的批处理，不是交互式延迟路径。**
标准改为：在 worker 中运行、不阻塞 UI、支持取消与进度上报、
**单次全市场 < 10 分钟**。110 秒达标。**不做任何以降低耗时为目的的优化。**

**2. `workbench-refactor.test.ts` 结构指纹失败是合法变更，不是回归。**

该测试是 N3 留下的护栏，断言 workbench 拆分后的结构不被意外改动。
Q2b 往 `screen-view.tsx` 与 `use-workbench-state.ts` 新增公式选股 UI，
指纹必然变化。这是 P2 已出现过一次的同类情况。

处理方式沿用 P2 的做法：**更新指纹并对新增部分单独精确校验**，
**不得删除或跳过该测试**。护栏的价值在于「意外改动会被发现」，
而不是「永远不变」。

**3. 全量测试下 `czsc.test.ts` / `signal-ledger.test.ts` 偶发文件级失败。**

两者单独运行均通过，全量运行时偶发失败（第二次全量运行即恢复正常）。
两者都经由单一串行 DLL worker。怀疑是全量负载下超过 `testTimeout: 20000`。

要求：**定位并消除偶发，不接受「重跑就好」**。
偶发失败会训练所有人忽略红灯，比稳定失败更危险。
若确认是超时，可为这两个文件单独放宽 timeout 并注明原因；
若是 DLL 并发进入，必须修串行化。
