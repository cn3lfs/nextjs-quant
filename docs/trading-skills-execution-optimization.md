# 交易 skills 策略化：执行效率优化方案

日期：2026-09-16。本文件只改**执行方式与批次粒度**，不改[原计划](trading-skills-strategy-plan.md)的目标、完成定义和覆盖要求：695 项方法仍需逐项落地，不按预想收益筛掉任何方法，效果仍留到回测判断。原计划 §5 分批表与 §8 验收纪律由本文件替换，其余章节继续有效。

管理分工：Claude 负责批次定义、验收门槛和进度核对；Codex 负责实现与验证执行。

## 1. 为什么要改

按机器清单当前状态与近期执行记录量化：

| 现象                    | 证据                                                                                        | 代价                                   |
| ----------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------- |
| 交付粒度过细            | 近 12 条执行记录每条交付 2–7 个预设                                                         | 剩余 552 项 `planned` 需 100+ 个循环   |
| 每个循环都做全量验证    | 每条记录均含全量 390 文件（300–335 秒）+ 完整 build（含 worker/runtime）+ Playwright        | 固定开销 × 100+ 次，远超实现本身       |
| 全量测试串行            | `vitest.config.ts` `fileParallelism: false`；`tests/setup-data-dir.ts` 已按文件隔离数据目录 | 391 文件串行，仅 81 个文件真的碰库/DLL |
| 全量结果没有干净信号    | 3 个既有失败（CRLF fixture、替换后 hash、工作台状态指纹）每批复述一次                       | 每批都要人工解释"无新增失败"           |
| UI 验证靠人工浏览器复核 | 每批 Playwright 核对菜单项数、新 ID 保存、390px 溢出、控制台错误                            | 机械断言用最贵的方式做                 |
| 同形测试逐批手写        | 每批 7–8 条"逐前缀回放/未来不改过去/T+1/受阻重试/公司行动证明/缺日零量非法 OHLC"            | 每个预设重复写一遍相同契约             |
| 记录冗长                | execution.md 每 2–7 个预设一段 5 段长文，含手工计数                                         | 撰写与计数核对成本随批数线性增长       |

## 2. 优化原则

1. **按完整功能批交付**：一个批次 = 一个可独立验收的功能族；批内子任务 = **一个来源文件全文**或一个 RK 分组，一次把该文件的全部方法做完，不再按 1–2 个预设切。
2. **验证分层**：批内定向（L1/L2），批末统一全量（L3）。全量测试、完整 build、Playwright 每批各一次。
3. **重复断言基建化**：同形契约做成共享测试套件，新预设注册即覆盖；UI 机械断言做成数据驱动测试。
4. **状态单一来源**：`docs/trading-skills-method-map.json` 是唯一进度源，脚本回填；execution.md 每批一条固定模板。
5. **不因效率牺牲正确性边界**：完整性目标、来源 hash 冻结审计、隔离 `QUANT_DATA_DIR`、通达信/Blocks 只读、禁止自动下单与外发、未来数据不改过去，全部不变。契约测试套件的断言项必须逐条列举，覆盖面不得低于原逐批手写。

## 3. 批次 E0：效率基建（前置，必须先做）

E0 不新增策略数量，是后续所有批次的固定成本削减，先做再继续家族批。

| 子项                      | 内容                                                                                                                                                                                                                                           | 验收                                                                      |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| E0-1 既有失败收口         | 逐个定位 3 个长期失败的真实原因（fixture 是否被换行规范化、hash 基线是否过期、工作台指纹是否为有意守卫）。属基线过期的修正基线并说明；属有意守卫的列入 `docs/known-test-failures.md` 并由 `verify:batch` 消费                                  | 全量输出要么 0 失败，要么失败集合与登记文件完全一致；不调整或绕过断言语义 |
| E0-2 全量测试并行化       | 拆 vitest 项目：碰库/DLL/临时目录/live 的文件保持串行，纯函数与纯计算文件开启 `fileParallelism`                                                                                                                                                | 通过/跳过/失败计数与当前串行基线逐项一致；记录优化前后耗时                |
| E0-3 分层验证入口         | `pnpm verify:spot <files>`（相关测试 + 受影响契约套件）、`pnpm verify:batch`（typecheck + 全量 + build 含 worker/runtime + 来源审计 + format/diff）                                                                                            | 两个命令可重复运行；批末只需一条命令，消除漏项与手敲差异                  |
| E0-4 共享契约测试套件     | 把逐批重复的断言做成注册驱动套件：完整历史前缀回放一致、追加未来数据不改过去、缺日/零量/非法 OHLC 不造信号、下一可成交时点执行、T+1 分批可卖、受阻重试与已确认退出不撤销、公司行动证明缺失拒绝交易模拟、卖出数量/步长/尾仓、资金守恒、排序稳定 | 契约清单成文；每个已实现预设自动进入套件；新增预设不注册则套件报缺失      |
| E0-5 注册表↔UI 一致性测试 | 用注册表全量枚举断言表单选项、ID 保存、参数清除、窄屏无横向溢出的可测部分，替代每批人工核对菜单项数                                                                                                                                            | 新增预设无需改测试即被覆盖；Playwright 降为批末一次、只走该批新增交互路径 |
| E0-6 声明式家族注册       | 家族内新增预设只写规则/参数/来源，注册表、表单选项、方法快照由家族 spec 派生；聚合器 `research-strategies.ts` 只做家族级拼接（已部分具备，补齐剩余家族）                                                                                       | 新增一个示例预设的改动面 = 家族文件 + method-map，不再四处同步            |
| E0-7 进度脚本回填         | 扩展 `scripts/audit-trading-methods.ts`：从注册表与测试用例反查 `status`/`implementation`/`tests`，回填 method-map；execution.md 采用 6 行固定模板                                                                                             | 手工计数取消；审计能指出"注册了但清单未更新"和反向漏项                    |

E0 完成后，单批固定开销从"每 2–7 个方法一次全量+build+Playwright"降到"每批一次"，并且全量本身更快、信号干净。

## 5. 分层验证规则（替换原 §8 的逐批全量）

| 层级        | 触发时机                 | 必须执行                                                                                   | 明确不执行                            |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------ | ------------------------------------- |
| L1 改动级   | 每次代码改动             | `pnpm verify:spot <改动相关测试文件>` + 受影响契约套件                                     | 全量测试、build、Playwright、桌面准备 |
| L2 子任务级 | 一个来源文件/RK 分组做完 | typecheck + 该家族全部测试 + 方法审计回填                                                  | 全量测试、Playwright                  |
| L3 批末     | 一个功能批全部子任务完成 | `pnpm verify:batch` 一次 + Playwright 一次（只走本批新增交互）+ 来源冻结审计 + format/diff | 无需每子任务重复                      |

例外（**批内允许追加一次全量**）：改动触及共享执行引擎（`research-execution.ts`、`research-portfolio.ts`）、注册聚合器、`indicators.ts` 或数据库迁移时，当次子任务结束即跑一次全量，不等批末。

桌面：`pnpm desktop:prepare` 仅在有意义的桌面交付前执行，不随批次固定执行。打包、提交、推送、外发仍各需单独授权。

## 6. 记录纪律（替换逐批长文）

- `docs/trading-skills-method-map.json`：唯一进度源。每项含 `status`（planned / implemented-variant / implemented）、`implementation`、`tests`、`boundary`、来源与规则版本；由 E0-7 脚本回填与校验。
- `docs/trading-skills-execution.md`：**每批一条**，固定模板：
  1. 批次与覆盖的方法 ID 区间、实际完成数与仍缺数；
  2. 关键工程定义与原文冲突的裁定（原文模糊处登记明确版本，不暗改规则）；
  3. 契约套件新增覆盖项；
  4. L3 验证结果（全量计数与耗时、build、Playwright、审计、format/diff）；
  5. 数据缺口与待办；
  6. 未做的事（未真实回测 / 未提交 / 未打包 / 未连生产库）。
- 子任务进度不写 execution.md，落在 method-map 与 `docs/decisions.md`（仅记录取舍与与预期不符的事实）。

## 7. 并行执行（可选，批内）

同一批内来源文件不相交、且家族注册文件不同的子任务，可分开 session 或 `git worktree` 并行；合并前各自跑 L2，合并后跑一次 L3。聚合器 `research-strategies.ts` 是唯一共享触点，冲突面小。跨批并行不做：B2 的风控组合是后续家族依赖。

## 8. 效率目标与核对方式

- 循环次数（**主要指标**）：剩余 552 项 `planned` 从 100+ 个验证循环降到 7 批 + 约 30 个子任务，L3 全量验证次数从 100+ 降到 ≤ 10 次。折算约 9 小时全量时间降到约 51 分钟。
- 全量耗时（**已结案，不再作为目标**）：E0-2 实测并行后 318.14 秒对串行基线 317.30 秒，无提速；分类器按能力闭包保守判定，294/396 文件仍串行。测量否证了"串行是主因"的原诊断，双项目划分保留但停止投入，理由与取舍见[决定记录](decisions.md)。**效率按 L3 次数衡量，不按单次耗时。**
- 改动面：E0-6 已实测——新增一个预设只改 2 个文件（家族文件 + method-map），临时探针预设验证后逐字节恢复。
- 断言密度（附带收益）：契约套件使断言从 2798 项增至 4802 项（+72%），全量仍 396 文件 0 失败、305.08 秒。这是 E0-4 的效果，不并入 E0-2 验收。
- 不变量：完整性目标、来源冻结、隔离数据目录、只读数据源、禁止自动下单与外发、未来数据不改过去。任何效率措施若削弱这些，撤回该措施而不是放松约束。
