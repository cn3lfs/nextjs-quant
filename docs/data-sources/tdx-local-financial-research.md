# 通达信本地财务数据使用调研

调研日期：2026-11-07。第1–8节保留最初只读调研时点的事实和建议；用户随后授权实施，并要求客户端数据处理统一归tstdx。当前实现、真实全目录结果与使用入口见[交付说明](../deliveries/2026-11-07-local-financial.md)，静态分析见[包内记录](../../packages/tstdx/docs/research/client-static-analysis.md)。

## 1. 结论

详细实施范围与验收已整理为[财务模块优化计划](../product/specs/local-financial-workbench.md)，用户确认先完成计划，业务实现尚未开始。后续补充核查发现 `gp*.dat` 同时包含股票、板块和市场序列：如 `gpsh880301.dat`、`gpsh999999.dat`，不能把原表中的 9,331 个文件全部理解为个股数据。正式分类和解析任务见计划 F0–F2。

本地数据已经足以支持财务筛选、成长与质量因子、个股多期对比，无须先采购新的财务数据。项目已有 DAT/ZIP 解析器和个股本地财务展示，应在此基础上接入批量研究。

优先顺序建议：**纠正现有字段语义 → 财务筛选与多期比较 → 技术条件和财务条件组合 → 有边界的历史研究**。当前下载的历史文件尚不能证明是完整的 point-in-time 数据；历史证券池与交易限制也需要独立证据。

## 4. 先纠正现有语义

字段编号依据本机 `tdx-doc` 技能所保存的官方《红宝书24》字典，位置为 `C:\Users\jm\.agent-skills\skills\tdx-doc\references\functions\专业财务数据字典.md`。官方编号从 1 开始，对应 DAT 的 `values[ID - 1]`；报告期另由包头取得，不能把 `values[0]` 当作报告期。

| 当前映射与文字                            | 实际官方字段                 | 应处理的问题                                                     |
| ----------------------------------------- | ---------------------------- | ---------------------------------------------------------------- |
| `longTermLiabilities: 68`，显示“长期负债” | ID 69，少数股东权益          | 不能参与负债计算；非流动负债合计应取 ID 62，总负债应取 ID 63     |
| `mainProfit: 74`，显示“主营利润”          | ID 75，营业成本              | 改为正确的成本字段及标签；毛利需要由收入减成本计算               |
| `netAssets: 270`，注释称包含少数股东权益  | ID 271，归属于母公司股东权益 | 明确为归母权益；所有者权益合计是 ID 72，两种口径不可混用         |
| `netProfit: 95`，统称“净利润”             | ID 96，归母净利润            | 与 ID 95 合并净利润区分，避免利润率、现金含量等比较混用主体      |
| 负债率使用流动负债与所谓“长期负债”相加    | 后者实际为少数股东权益       | 现有“财务包口径下界”说明不能为错误分子背书，应改为 ID 63 / ID 40 |

最新包全部 5,573 条记录都满足以下两式，核查容差为 `max(1, 两侧绝对值) × 1e-5`：

- 资产总计 ID 40 ≈ 负债合计 ID 63 + 所有者权益合计 ID 72。
- 所有者权益合计 ID 72 ≈ 归母股东权益 ID 271 + 少数股东权益 ID 69。

例如本地茅台三季报的 ID 69 约为 92.17 亿元，ID 62 约为 3.63 亿元，二者显然不是同一负债字段。上述核查支持字段语义，但不是逐条公开财报的独立核验。

旧实现通过与协议快照数字匹配确定槽位，只能证明两个来源的数字相同，不能证明旧协议字段名准确。本轮仅记录问题，未修改上述代码。

| 时点       | 314 财报公布日期                                                             | 本批为 YYMMDD 整数；需补足前导零，不能套用只接受 YYYYMMDD 的现有转换函数 |

优先产品用途：

1. **财务底线筛选**：利润、扣非、现金流、资产负债率、商誉占资产等条件组合，缺失独立列示；不要直接给全行业统一“合格分”。
2. **成长强势池**：已有 RPS/技术条件与收入、单季扣非增速结合，显示每条条件的值、报告期和原因。
3. **质量比较**：ROE、毛利率趋势、现金流与利润关系、应收/存货相对收入变化；银行、保险、券商单独解释。
4. **个股多期面板**：至少最近 8–12 期的累计、单季和 TTM，直接查看增长加速、利润与现金流背离。
5. **估值辅助**：PE TTM、PB、PS TTM；必须有对应时点的未复权价格和股本/每股指标口径，亏损或非正权益不能输出误导性估值。

本地最新包具备计算这些字段的基础；有效性仍需逐字段确认。零不能一律当成缺失，也不能一律当成有效值，尤其是金融类不适用项目和空槽位。

TTM 交叉核验：最新包有 5,447 条记录同时具备 2025 年报、2025 三季报、2026 三季报；`2025 年报归母利润 + 2026 三季累计归母利润 - 2025 三季累计归母利润` 与 ID 308 × 10,000 全部落在输入金额规模的 float32 与金额取整容差内。本轮使用 `2e-6 × max(1, 三个输入绝对值, TTM 绝对值) + 100 元`；这验证了本地 TTM 字段量级与口径的一致性，未核验其他所有 TTM 字段。

## 6. 历史研究的时点边界

全量 294,884 条记录中，ID 314 有 97 条为零；其余 294,787 条在按 YYMMDD 补零并按报告期时代解析后均可还原为有效日历日期，未发现早于报告期的日期。最近 11 个有效包（2024 Q1 至 2026 Q3）该字段全量非零。最新包的日期范围为 2026-10-10 至 2026-11-06。

但还存在两类证据限制：

- 135 条记录的公布日期恰好等于报告期末，集中于 1991–2002、2005、2010 年。不能仅凭格式合法认证它是真实公告日，应标记待核验并排除严格时点研究。
- 当前旧报告期包的公布日期可能远晚于报告期：例如 2024 年报包最晚为 2026-10-26。仅凭现有单一版本无法区分首次披露、补报、纠错或来源更新；也不能证明同一行其他字段在该日期前后没有被修改。

建议最小契约包含：`symbol`、`reportPeriod`、`announcementDate`、`availableFrom`、`downloadedAt`、`sourceSha256`、`fieldMappingVersion`、字段单位、缺失/异常原因。不能从文件 mtime 推断首次公开日期。

历史查询必须接受明确的 `asOf`，先按可见时间过滤，再在可见记录中取最近报告期。只有公告日期、没有公告时刻时，保守使用公告日之后的下一交易日起生效；五分钟策略不可在公告当日早盘提前取数。日期缺失或可疑不能按季末加固定天数补造。

累计、单季、TTM 的每个组成项都要在该时点可见且主体一致；缺少必要期数时返回缺失。报告发布后的财务值可持续使用，但必须显示报告年龄和业务新鲜度规则，不能跨缺失期伪造新报表。

即使按公告日滞后使用，仍需披露“当前下载版本的历史财报研究，未认证首次披露版本”。后续保存每次下载时的版本可以建立前向版本链，不能反向补出过去不存在的快照。严格历史绩效还取决于当时证券池、公司行动与交易限制，不仅是财务日期。

## 7. 推荐落地阶段与验收

| 阶段            | 交付                                                                                   | 验收重点                                                                                         |
| --------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |

现有五分钟单证券回测可以将低频财务条件作为输入门槛；多证券横截面选股、调仓和资金竞争是额外范围，不应为了财务接入顺手扩成组合回测引擎。通达信公式 FINVALUE/FINONE 的全面兼容也属于独立工作，首批无需以此为前提。

先按财报包批量读取与投影，复用当前进程内缓存；是否需要独立持久索引由筛选延迟和版本保存需求决定，不先引入常驻全量导入。若后续需要数据库迁移，再按仓库约束使用隔离目录验证。
