## 1. 缺陷一：重复列名的费用列被整列丢弃（**佣金全部读成 0**）

真正的交割单表头里**有两个「佣金」列**：

```
成交日期 证券代码 证券名称 操作 成交数量 成交均价 成交金额 可用余额 发生金额
佣金(第9列,全为0) 印花税 其他杂费 资金余额 合同编号 过户费 佣金(第15列,真实值) 结算费
```

第 9 列是占位、恒为 0，第 15 列才是实际佣金（0.78 / 0.80 / 0.79…）。
当前 `mapDeliveryColumns` 对非 `otherFee` 字段是「第一个匹配的列生效，其余进 duplicates
被丢弃」，于是**全部 2776 笔的佣金都读成 0**，并连带产生 1109 笔费用核对异常。

### 要求

- 把 `otherFee` 已有的多列累加机制**推广到所有费用分项字段**：
  `commission`、`stampTax`、`transferFee`、`otherFee` 一律多列累加。
  **`feeTotal` 例外**——它是合计值，重复时相加会翻倍，
  取第一个非空列，若多列值不一致则告警。
- 在 `ColumnMapping` 里显式暴露每个费用字段用到的列（不要隐式行为）。
- 累加对「占位 0 + 真实值」这种情况天然正确，不要去猜哪列是占位。

## 2. 缺陷二：「可用余额」未映射

交割单的「可用余额」是**股份可用余额**（卖出后为 0、买入 800 后为 800）。
当前未匹配任何别名，进了 `unmapped`。

### 要求

`balanceShares` 增加别名 `可用余额`。注意不要与 `资金余额`（`balanceCash`）混淆。

## 3. 缺陷三：银证流水里的**作废记录**被当成有效转账（影响 13 万）

流水导出包含失败/作废的转账，「摘要」列写 `作废`，「备注」写明原因：

| 备注                                   | 摘要 | 笔数 | 金额 |
| -------------------------------------- | ---- | ---- | ---- |
| `出入金失败，原因@@…`                  | 作废 | 2    | —    |
| `E1111-余额不足，可用余额为@@…`        | 作废 | 3    | —    |
| `成功` / `M0001-交易成功` / `交易成功` | 成功 | 95   | 有效 |

真实数据里这 5 笔作废合计 **130,000 元**，全部被当成有效入金，
导致推算的期末现金比柜台记录的多出 13 万。**资金曲线、收益率、夏普全都会错。**

### 要求

- 资金流水行必须检查**状态/摘要列**。状态明确为失败/作废的（`作废`、
  含 `失败`、含 `余额不足`）**不计入现金流**，归入 `unresolved` 并写明原因
  （不要静默丢弃——用户要能看见这几笔）。
- 状态列缺失时按现状处理（视为有效），但在 `diagnostics` 里说明"未找到状态列，
  无法排除失败流水"。**不要假定没有状态列就一定都是成功的。**
- 状态词表要可维护，且遵循「未知不猜」：无法判断的状态不要当成失败。

## 4. 缺陷四（R4 相关）：应优先使用交割单自带的「资金余额」

真正的交割单每笔都带「资金余额」——**柜台记录的权威现金余额**。
管理者验证：按 `(日期升序, 同日内原始行序)` 重放，
`余额[i] - 余额[i-1] == 发生金额[i]` 在 2801 笔里只有 121 处不成立，
而那 121 处正是交割单之外的资金事件（银证转账、分红等），
按日聚合与流水+分红核对后残差仅 `7303.35`。

首笔还能直接反推**期初现金 = 10000.00**，与流水首笔转入完全一致。

### 要求

- `trade-review-nav.ts` 的现金序列：**若 fills 带有 `balanceCash`，
  优先以它为准**，推算值仅用于交叉校验；两者不一致时报告差异，
  **不要静默选一个**。
- 期初现金可由首笔的 `余额 - 发生金额` 反推；反推值与调用方传入的
  `openingCash` 冲突时，报告冲突，不要擅自覆盖。
- **注意排序**：导出文件按日期倒序但同日内正序，
  必须按 `(日期升序, 原始行序升序)` 还原时间轴。
  管理者用错误排序时得到 2756 处跳变，正确排序后只剩 121 处——
  这是验证排序是否正确的有效自检，请在测试里固化。
