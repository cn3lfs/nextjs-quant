# 任务书 U4：执行质量与执行损耗

依赖 [U1](u1-daily-performance.md)。U 系列里业务价值最高的一批。

来源：czscflow `apps/web-antd/src/views/trader/components/execution-cost.vue`
（1585 行，滑点 BP / 滑点成本 / 总执行成本 / **执行损耗**）。

## 1. 问题

R1–R13 把交割单的费用明细做透了：佣金、印花税、过户费、杂费、
逆回购本金、价格除数、零金额伪成交，全部核对到位。
但我们**从没做过「理论 vs 实际」的对照**。

复盘最该回答的问题是：**亏的钱里，有多少是选股选错了，有多少是买卖得太差？**
现在这个问题答不了。

czscflow 的 `执行损耗 = 账户收益 − 组合理论收益` 思路对，
但它的「预期价」来自实盘下单系统的委托价，我们没有这个数据。

## 2. 基准价口径（用户已定：当日 VWAP）

**先说一句多市场的事。** 用当日 VWAP 当「预期价」，
根本原因是 **A 股交割单没有委托价**——这是 A 股数据的限制，不是普适口径。
BTC / 外汇的成交回报里有真实委托价和挂单簿，届时应该直接用委托价，
那才是滑点的标准定义。

所以：把基准价口径定义成一个**具名可辨识联合**，
当前只实现 `dayVwap` 一个变体，结果里回显用的是哪个口径。
以后加 `orderPrice` 是新增变体，不是改写。本批**不实现第二个变体**。

`VWAP = bar.amount / bar.volume`。

**这个除法 `trade-review-market.ts` 已经有了**——R12 用
`const average = bar.amount / bar.volume` 做价格除数校验。
必须复用同一个入口，不许在 U4 里重写一遍（`invariants.md §1`）。

### 2.1 硬边界

A 股交割单**没有委托价**。「预期价」只能是可独立核对的公开基准。
以下几条是红线，写进 `invariants.md`：

- **不得编造委托价**，不得用「当日均价」以外的任何推测值
- `bar.volume <= 0` 或 `bar.amount <= 0` 时 VWAP 不可得，
  该笔成交**不出滑点数字**，标 reason，不用收盘价顶替
- **逆回购（204/131 前缀）整体排除**——没有有意义的 VWAP，
  沿用 R10/R11 已建的排除逻辑
- **可转债的数量单位**按 R12 已核对的口径处理（面值 100/1000），
  单位错了 VWAP 会差两个数量级
- 一字板、停牌复牌首日等 VWAP 仍然可得但参考意义弱，**照常出数**，
  不做主观剔除；页面提供「按成交额过滤」让用户自己判断

## 3. 交付

### 3.1 逐笔执行质量 —— `src/lib/execution-quality.ts`（纯函数）

对每笔 `ParsedFill` 算：

```
不利滑点BP = 买入 ? (price − vwap) / vwap × 10000
           : (vwap − price) / vwap × 10000
滑点成本   = 不利滑点BP / 10000 × amount
```

**符号约定：正 = 不利**（买贵了 / 卖便宜了）。这条要在类型注释和页面上都写明，
否则「正滑点」会被读反。czscflow 页面上「正滑点/负滑点」筛选项没说明方向，
不要抄这个坑。

每笔返回：`{ tradeDate, code, name, kind, price, vwap, slippageBp, slippageCost,
fees.total, amount }`，全部字段用 `ReviewValue` 承载缺失。

### 3.2 汇总

- 总佣金 / 总印花税 / 总过户费 / 总杂费 / 总费用（直接来自已入库的交割单，不重算）
- 总滑点成本、平均不利滑点 BP（**按成交额加权**，不是简单平均——
  czscflow 用的简单平均会让一笔 1000 元的烂成交淹没一笔 100 万的好成交）
- **总执行成本 = 总费用 + 总滑点成本**
- 成本占总成交额比例（BP）
- 分组汇总：按标的、按方向（买/卖）、按月

### 3.3 执行损耗 —— 反事实重放

这是 U4 的核心，也是对 czscflow 的改进。

**定义：把同一批成交的价格全部换成当日 VWAP，数量、日期、标的、费用一律不变，
重新跑一遍 `reviewTradeNav`，得到假想净值。**

```
执行损耗 = 实际 TWR − VWAP 反事实 TWR
```

这个定义的好处是**完全自洽**：不依赖 E3 的理论组合，不需要任何新数据源，
把「选股能力」彻底剔除掉（标的和数量完全相同），
剩下的差额**只能**来自成交价格的好坏。

实现上就是构造一份 `fills` 副本、替换 `price` 与 `amount`
（`amount = vwap × quantity`，费用保持原值），再调一次现有的 `reviewTradeNav`。
**不要 fork 一份净值逻辑**——整个 R4–R13 的净值口径必须原样复用。

约束：

- 任何一笔成交的 VWAP 不可得 → **整个反事实重放不可得**，
  返回 `null` + 「N 笔成交缺少可得 VWAP（列出日期与代码）」。
  不允许「缺的那几笔用原价」——那样算出来的损耗是假的。
- 反事实净值同样可能因为缺行情、非正本金等原因中断，
  沿用 R9 的分段 TWR 处理，不新造规则。
- 两侧的 TWR 必须走**同一分段口径**才能相减；分段边界不一致时不出数字。

### 3.4 页面

`/trade-review` 新增「执行质量」区块：

- 顶部 4 个指标卡：总执行成本、总滑点成本、平均不利滑点(BP，成交额加权)、执行损耗
- 执行损耗卡片下方一行说明：
  「实际净值与『同样标的同样数量按当日均价成交』的净值之差，
  只反映成交价格好坏，不含选股优劣」
- 逐笔明细表：`DataTable`，**服务端排序分页**（真实账户成交笔数上千）
- 筛选：标的搜索、买/卖、不利滑点 > 5BP、日期区间
- 分组汇总表：按标的 / 按方向 / 按月，可切换
- CSV 导出（czscflow 有，确实实用）；**导出必须走已有的账号脱敏路径**
  （R2 已建），不得输出账号

## 4. 测试

`tests/execution-quality.test.ts`：

- 手算 fixture：买入贵于 VWAP、买入便宜于 VWAP、卖出两个方向，
  注释里写出 BP 算式，用计算器可复核。
- 成交额加权平均 vs 简单平均给出不同结果的用例，断言用的是加权。
- `volume = 0` / `amount = 0` → 该笔 `null` + reason，且整个反事实重放不可得。
- 逆回购成交被排除，不进入任何分子分母。
- 可转债数量单位用例（沿用 R12 已有 fixture）。
- **反事实重放一致性**：所有成交价恰好等于 VWAP 时，执行损耗必须为 0
  （浮点容差内）；这条是整个 §3.3 的正确性锚点。
- 导出内容断言不含账号（沿用 R2 已有的脱敏断言写法）。

## 5. 验收

- 真实账户能出四个指标卡，执行损耗有数字或有明确的不可得原因。
- 不利滑点符号方向在页面上写明，人工抽查 3 笔成交能用
  「成交额/成交量」手算复核到一致。
- 缺 VWAP 时整段损耗留空，**不出现任何用原价/收盘价顶替的分支**
  （`invariants.md §5`「宁可留空，不可给假数」）。
- 逐笔表服务端分页，页面无障碍树不因成交笔数增长而爆炸。
- 导出不含账号。
- `invariants.md` 补上 §2 的 VWAP 口径与红线。
- `pnpm check` 通过；真实账户浏览器验收由管理者执行。
- 本批不新增迁移（滑点是从已入库数据算出来的派生值，不落库）。

## 6. 明确不做

- 不接 E3 理论组合做对照（那是 U7 权重回测范式的事，另行评估）
- 不引入 tick / 分笔数据来还原「更真实的委托价」
- 不做择时建议（「你应该早半小时买」这类结论没有证据支撑）
