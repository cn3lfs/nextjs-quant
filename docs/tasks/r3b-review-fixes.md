## 1. 缺陷一：移动加权因浮点误差误判「开仓成本未知」

### 现象（真实数据）

| 口径 | 平仓回合 | 可计收益 | 净收益合计 |
| --- | --- | --- | --- |
| movingAverage | 785 | **769** | **-190,051.02** |
| fifo | 785 | **784** | -230,731.06 |

同一份数据、全部完全平仓，两种口径的**可计收益回合数差了 15 个，净收益差 3.9 万**。
你在 R3 报告里也写过「完全平仓的总收益必须相同」——这里违反了。

### 根因

```ts
const fraction = available ? needed / available : 0;
lots = lots.map((l) => ({ ...l, quantity: l.quantity * (1 - fraction), ... }));
```

移动加权按比例缩减每个 lot 的数量，多次部分卖出后 `quantity` 累积浮点误差，
`available` 变成 `2199.9999999996`。随后：

```ts
const unknown = available < f.quantity;   // 2199.9999999996 < 2200 → true
active.unknown ||= unknown;
```

整个回合被判「开仓成本未知」，收益作废。FIFO 用整数扣减，不受影响。
被误判的都是多次部分买卖的标的，例如 `sh600703`、`sh600782`、`sh601669`。

### 要求

- 持仓数量的比较与判定**不得被浮点误差影响**。
  推荐做法：移动加权本就不需要保留 lot 明细，改为维护聚合的
  (总数量, 总金额, 总费用)，数量按整数扣减；若保留现结构，
  则数量比较必须带容差且扣减后归整。**不要只在比较处加 `1e-6` 了事而让
  `available` 继续漂移**——漂移会一路传到 `remainingQuantity` 和均价。
- `openingUnknown` 是**数据事实**（真的不知道开仓成本），
  必须与成本口径无关：同一标的在两种口径下的 `openingUnknown` 必须一致。

## 2. 缺陷二：费用用分项求和，与实际资金变动对不上

### 现象

FIFO 口径股票净收益 `-225,375.76`，而按「发生金额」独立汇总为 `-225,482.08`，
差 `106.32`。单笔例子（`sh601919` 中远海控）：

```
买入 100 @12.00  成交金额 1200.00  手续费 0.15…  发生金额 -1200.15
卖出 100 @16.58  成交金额 1658.00  手续费+印花税 1.87…  发生金额 +1656.13
实际净收益 = 1656.13 - 1200.15 = 455.98
引擎给出   = 456.03   （费用合计算成 1.97，实际 2.02）
```

### 根因

引擎用 `fees.commission + stampTax + transferFee + otherFee` 求和。
但该券商的交割单**费用分项不完整**（过户费等未单列），
而「发生金额」是柜台记录的**实际资金变动**，是权威值。
单笔差几分钱，2000 多笔累计就是上百元，且**与银行流水永远对不上账**。

### 要求

- 当 `netAmount` 可得时，实际费用优先**反推**：
  买入 `fees = |netAmount| - amount`；卖出 `fees = amount - netAmount`。
  反推值为负（数据自相矛盾）时不得使用，退回分项并在 `warnings` 说明。
- `netAmount` 不可得时才用分项求和；两者都没有时费用为 `null`
  （既有「实际费用缺失」语义保留）。
- 在回合里明确记录本次费用的来源口径（反推 / 分项），不要让用户猜。
- 逆回购汇总同样遵循此口径。
