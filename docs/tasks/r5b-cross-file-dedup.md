# 任务书 R5b：跨文件去重与零值编号（两个阻断性缺陷）

管理者用三份真实文件做端到端验证（导入交割单 → 导入成交明细 → 生成快照），
在第二份文件就被阻断。两个缺陷都会让功能不可用。

## 0. 不可越界

- 只改 `src/lib/delivery-import.ts`、`src/server/delivery-store.ts` 及其测试。
- 不改迁移、`mcp.ts`；不 commit / push / 打包；不新增依赖。
- 既有用例必须继续通过；与修复冲突的先报告，不要擅自改断言。

## 1. 缺陷一：`"0"` 被当成有效的成交编号（**导致整批回滚**）

成交明细里，分红/扣税等行的「成交编号」列写的是 `0`。
`text(cells, "dealId")` 返回字符串 `"0"`（truthy），于是走了「有成交编号」分支：

```
fingerprintSource: ["cash","deal","0","2025-01-10"]
```

同一天所有编号为 `0` 的行**指纹完全相同**。真实数据里 2025-01-10 有两笔
（`300398 飞凯材料` 股息红利扣税 `-21.00` 与 `-3.60`），
指纹相同但金额不同 → 判为冲突 → **整批事务回滚，成交明细完全无法导入**。

### 要求

- 编号类字段（`dealId`、`orderId`）的**零值等同缺失**：
  `0`、`0.0`、`0.00`、`000`… 这类**全零**（可带小数点）的值视为没有编号，
  退回按经济身份 + 出现次序生成指纹。
- **注意**：真实成交编号可能以 0 开头（如 `0105000019041204`），
  **不得**用「去掉前导零后为空」或「转成数字等于 0」之类的粗暴判断误伤它们。
  只有整个字符串除 `0` 和 `.` 外没有其他字符时才算缺失。

## 2. 缺陷二：跨文件无法去重（**同时导入会让成交翻倍**）

用户的两份文件描述**同一批成交**，但字段互补：

| | 成交明细 | 交割单 |
| --- | --- | --- |
| 成交编号列 | **有** | **无**（只有合同编号） |
| 备注列（识别分红/配号/中签） | **有** | 无 |
| 过户费、资金余额 | 无 | **有** |
| 成交笔数 | 2775 | 2776 |

因为一份有成交编号、一份没有，两者指纹格式不同，
**2871 行里「重复 0 笔」**——全部当成新增。同时导入两份，成交就会存两遍，
持仓、盈亏、资金曲线全部翻倍。

管理者已核实：两份文件的 `(日期, 代码, 方向, 数量, 价格)` **完全一致**
（按此键比对，仅在交割单多 1 笔、仅在成交明细 0 笔）。

### 要求

- **指纹统一改为「经济身份 + 组内出现次序」，不再使用 `dealId` 分支。**
  经济身份 = 日期 + 代码 + 买卖方向 + 价格 + 数量（现金流为 日期 + 类型 + 金额 + 代码）。
  `dealId` / `orderId` 仍然保存在 payload 里作为证据，只是不再参与指纹。
  这样同一笔成交在两份不同格式的导出里得到**相同指纹**，跨文件去重才可能成立。
- 出现次序沿用现有 `occurrenceCounter` 机制（已验证跨导出稳定）。

## 3. 缺陷三（由缺陷二引出）：冲突判定过严

两份文件对同一笔成交的**费用记录本就不同**：交割单有过户费、成交明细没有；
`rowIndex` 更是文件内位置，跨文件必然不同。
当前冲突比较用**完整 payload**，这些差异会被误判为「编号已用于不同内容」。

### 要求

- 冲突判定只比较**核心经济事实**：
  日期、代码、买卖方向、价格、数量、成交金额、发生金额。
  这些一致 → 判为 `duplicate`（跳过，保留先导入的记录），**不是冲突**。
- 位置字段（`rowIndex`）、来源特有字段（费用分项、余额、编号、备注）
  的差异**不构成冲突**。
- 核心经济事实**真的不同** → 仍然整批回滚并报错（这个既有语义必须保留）。
- 在导入结果的 `diagnostics` 里说明：有多少笔因已存在而跳过，
  保留的是先导入的版本。让用户知道「想要交割单的过户费就先导交割单」。

## 4. 测试要求

1. 零值编号：`成交编号=0` 的两行（同日、同代码、不同金额）能各自成为独立记录，
   不再冲突；`成交编号=0105000019041204` 这类以 0 开头的**真实编号不受影响**。
2. 跨文件去重：用 `ths-settlement.txt`（交割单，无成交编号）与
   `ths-history.txt`（成交明细，有成交编号）中**描述同一笔成交**的行构造样本，
   断言两者指纹相同、第二次导入判为 `duplicate`、库内只有一条。
3. 冲突判定：构造两笔核心经济事实相同但费用分项不同的记录 → `duplicate`；
   构造价格不同的记录 → 仍然冲突并整批回滚（逐表 count 断言回滚彻底）。
4. 既有的幂等、撤销、脱敏用例继续通过。

## 6. 管理者的真实数据验收锚点（你无法自证）

依次导入交割单 → 成交明细 → 两份流水后：

- 成交总数应在 **2776** 左右（成交明细相对交割单只多/少个位数笔），
  **绝不能接近 5551**（那说明没去重）；
- 成交明细导入**不得整批回滚**；
- 现金流应包含分红、扣税、中签，以及两份流水的有效转账（作废的除外）。
